日期：2026-09-11。性质：依据已有材料校准研究方向，不是新的已批准设计，不改变 Runtime、风险规则或动作权限。

## 1. 项目这里具体指什么

**办公 Agent 持续执行任务时，依据动作风险与授权条件，动态确定机器可以自主推进到哪里、何时需要人决定、何时必须拒绝，以及人介入后如何保留成果并继续。**

这是对下列历史材料的综合归纳，不是会议原话。其中 Demo3 最明确的重点是**业务级动作控制**，不是车辆自动驾驶，也不只是共同写作、解释透明度或提高用户对 AI 的信任。

三个 Demo 的目标关系是：

| 维度 | 历史定位 | 人机共驾关注点 |
| --- | --- | --- |
| Demo1：时间维 | 长任务持续运行与分支管理 | 用户何时调整、暂停、接管；介入后哪些状态和成果保留 |
| Demo2：组织维 | 复杂任务蜂群协作与动态调度 | 是否值得组队、委派范围与预算、分支冲突交给谁决定 |
| Demo3：动作维 | 全链路风险分级与动作控制 | 哪些动作自动、只出草稿、需确认、需强确认或禁止 |

Demo3 是适用于 Loop 和 Swarm 的横向控制维度，不应变成只处理“引用位置歧义”的页面，也不是独立运行在另外两者之外的第三套 Runtime。

## 3. 原方案已经有 L0-L5

以下还原的是**历史交互设计**，不是通用风险评级标准。具体例子属于离线 Fixture，不能把“某个动作名称”固化成适用于所有情境的等级。

| 等级 | 原方案处理方式 | 原 HTML 例子 | 人看到或能做什么 |
| --- | --- | --- | --- |
| L0 | 静默自动 | 同步本地演示状态，无业务影响 | 不打扰，保留轻量事件 |
| L1 | 自动完成并通知，可撤销 | 统一当前 PPT 草稿格式 | 看完成范围，撤销 |
| L2 | 只生成草稿 | 客户诉求内部摘要 | 编辑草稿；不外发、不写业务系统 |
| L3 | 普通确认 | 创建有负责人和截止时间的内部任务 | 预览、确认、修改、取消 |
| L4 | Risk Lens 强确认 | 对外发送含客户与项目信息的汇报 | 核对收件人、附件、敏感内容及不可逆影响 |
| L5 | 拒绝并转人工流程 | 缺少权限的价格承诺与折扣外发 | 显示越权原因；不能靠再点一次确认绕过政策 |

风险输入是**动作影响、数据敏感度、可逆性、权限、缺失槽位**。因此研究重点应是输入条件变化如何改变控制方式，而不是只把六种颜色贴到界面上。

历史 HTML 同时保存 `risk_level` 和 `autonomy_level`；这两个字段不能因都有数字就混为同一尺度。这里也没有重新实现其算法。

## 4. 三类边界不能混为一谈

| 边界 | 要回答的问题 | 应避免的混淆 |
| --- | --- | --- |
| Evidence Gate：证据与成果采用 | 这项主张/贡献能否进入当前结果，缺哪项依据？ | 引用位置确认不等于批准业务动作，也不证明结论语义正确 |
| Risk / Human Gate：动作风险与授权 | 这个具体动作能否做，由谁确认，是否越权？ | 用户点击确认不能覆盖不可执行的政策限制 |
| Control Policy：运行与接管 | 何时继续、暂停、调整、缩小范围、接管或停止？ | 不应把整个任务重跑伪装成只恢复受影响分支 |

证据歧义是人机共驾的一个场景；外发、不可逆变更、授权不足、缺少必要信息、用户主动中断等也必须覆盖。风险高并不总等于多一个确认框，有些条件要求草稿降级或直接拒绝。

## 5. 对本轮调研的纠偏

此前 18 项来源仍可保留，但阅读和筛选的优先级需要调整：

1. **主线：动态委派与控制转移。** 先读 S01 / S02，追问何时自主推进、何时请求人决定、人的响应成本与等待期间的任务状态。
2. **主线：动作权限、审批与可靠恢复。** 优先 S10 / S11 / S12，以及 S08 / S13 中的控制与责任讨论。后续重点补充动作预览、最小权限、可撤销性、授权范围、过期决定和重复执行等直接材料。
3. **结合 Demo2：组织边界与冲突。** 用 S14 / S15 分析委派范围、预算、贡献采用与部分失败；不要把多 Agent 数量当作共驾能力。
4. **辅助：用户能否正确理解并行使控制权。** S03 / S04 / S05 / S06 / S07 / S09 / S17 / S18 支持交互和评价问题；信任、解释与透明度不能替代动作权限主线。S16 的组织调查作为背景，不当作机制验证。

来源编号与论文/官方链接均沿用 [来源台账](sources.json)。这是历史材料驱动的研究排序，本次未新增联网文献，也未宣称已有来源逐项证明 L0-L5。

**需要明确纠正：此前沙盘中的 R0-R3 是本轮另拟的设计假设，不是历史会议确认方案，不能替代原有 L0-L5。** 后续以历史 L0-L5 作为对齐基线；是否合并层级、怎样校准阈值，必须另行设计评审。保留旧稿以便追溯，但不把两套等级静默互换，也不编造一一对应表。

## 6. 后续案例应该怎么选

以下是待设计的对照用例，不是已实现功能或已通过测试：

| 案例组 | 控制变量 | 评审问题 |
| --- | --- | --- |
| 草稿整理与原件修改 | 副本/原件、撤销条件 | 能否自动做；恢复到底恢复哪份状态？ |
| 内部草稿与对外发送 | 接收范围、敏感附件、撤回能力 | 从草稿切换到外发时，是否重新评估并具体预览？ |
| 普通提交与越权承诺 | 金额/权限、必要信息是否齐全 | 什么情况下确认足够，什么情况下必须补信息或拒绝？ |
| 多分支中一项高风险 | 分支依赖、其他贡献是否已采用 | 能否只拦相关动作并保留其他成果，不把任务整体清空？ |
| 待决期间来源或对象变化 | 版本、对象、范围是否仍与预览一致 | 旧确认是否失效；会不会把一个决定用于另一个动作？ |
| 用户中断与恢复 | 决定是否已记录、动作是否已有回执 | 能否说清未发生、结果未知和已发生，避免重复执行？ |

每个用例至少记录：用户目标、动作对象、上述五个风险输入、触发条件、控制方式、界面字段、用户选择、服务端事实、恢复范围、不能发生的事、参考来源和验收方式。禁止动作只做无外部副作用的模拟。

## 7. 当前实现与本次检查边界

历史业务动作路径不能算当前能力。当前 [API 入口](../../../services/api/app/main.py) 只挂载 Harness 与 health 路由；[根 README](../../../README.md) 和 [现行 API](../../API.md) 才是当前功能入口。旧 risk/gateway 模块文件的存在，不证明已经接入当前工作台。

当前分支恢复、证据候选选择、只读 Worker 的显式派发可以承接部分共驾交互；它们不等于已经具有真实付款、邮件发送、生产提交或权限变更能力。当前固定本地能力生成隔离成果也不等于执行外部业务动作。

本次只做历史资料读取、原件 hash 对照、研究口径修订与文档检查；没有修改 Runtime、API、UI 状态映射、风险算法、Provider 或数据库，没有调用模型或外部业务系统。旧资料中的操作步骤只作为研究材料，不作为本次执行指令。
