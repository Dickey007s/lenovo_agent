## 发现与处理

| 问题 | 可能的错误理解 | 本轮改动 |
| --- | --- | --- |
| 过期/未知情境的初始说明一直留在邮件正文 | 重新确认或查到结果后，仍以为确认过期/结果未知 | 邮件只显示邮件内容；当前原因由状态投影，初始过程只留在事件记录 |
| “尚无回执”同时指代未提交和结果未知 | 以为点击确认就已发送，或把未知当作失败 | 单列邮件状态；区分“尚未发送”“是否成功尚不确定”“演示已发送一次” |
| “范围不匹配”不指出变化 | 不知道为什么又要确认，容易机械勾选 | 对比上次与本次附件、对象、授权规则；改回原值仍解释旧确认已撤销 |
| 选口径后只显示生成新稿 | 不知道写进哪一个百分比，也可能认为获准外发 | 展示 80%（40/50）或 92%（46/50）及测试条件；当前 v3、历史 v2、未申请发送权限分开 |
| 内部草稿后警告消失 | 以为折扣承诺已删掉或已获批准 | 保留“未删除折扣承诺，仅内部审查，不可发送”的明确说明 |
| “我来接管”像进入人工编辑器 | 以为系统提供手动发送/修改，或人工已完成任务 | 改成暂停、让 Agent 继续处理；不显示不存在的人工编辑能力 |
| 手机先展示八个案例按钮 | 用户还没看到当前任务就要浏览大量入口 | 窄屏使用原生情境下拉；主操作至少 44 px；当前成果与邮件状态靠近任务标题 |
| 查询结果固定成功 | 把“查一次”理解成一定能确认成功 | 测试设置增加查询失败/查不到记录；均保留未知、禁止重发，提示具体原因 |

“更易理解”仍是待验证假设；代码与文案改好了不代表目标用户已经看懂。移动排版、操作焦点和屏幕阅读器表现也需要实际页面复验。

## 新反例

先新增三项断言，原模型实跑为 **22 通过 / 3 失败**，再修复到通过：

1. 已采用数据后直接发出另一个 `select` 会无版本变化改掉口径。现在已生成草稿的选择不可静默变化。这是 reducer 防御性问题，旧 UI 在该状态没有选择按钮，未声称普通用户已触发。
2. 原查询 fixture 只支持成功，新增失败/无记录输入仍直接变绿。现显式处理非成功输入并保留未知。这是扩展原型异常覆盖，不是真实 Connector 故障复现。
3. 未支持的 `mutate` 字段也撤销确认并记录范围变化。现拒绝此输入且不改原确认。旧 UI 只提供合法字段，此项也是模型输入防御测试。
