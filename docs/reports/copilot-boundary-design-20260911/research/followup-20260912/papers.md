# 下一轮人机共驾调研：先看合作过程，再看有效监督

2026-09-12。定向增量 6 篇，与既有 26 项按主标题、主 URL 去重。不是系统综述，也不是本项目的用户研究。详细作者、版本、阅读范围、原文位置与反例见 [结构化台账](papers.json)。

## 最值得先读的三篇

1. **Cocoa**：先回答“人除了批准，还能怎样参与”。共同计划和共同执行并不需要分成僵硬的两个阶段。我们优先研究的是修改一个中间结果后如何继续，以及如何让用户知道某一步由谁负责；不是直接照搬它的文档编辑器。原文的控制感结果不等于客观理解已改善。[作者 CHI 2026 论文](https://kevinpjk.github.io/assets/pdf/cocoa_chi_2026.pdf)
2. **Plan-Then-Execute**：接着看反证。形式清楚、可编辑的计划仍可能被误信，增加参与也可能增加负担。下一次用例不能只有“错误被用户修好”，还要包含“正确方案被人改错”和“用户觉得放心却漏掉错误”。[正式出版页](https://research.tudelft.nl/en/publications/plan-then-execute-an-empirical-study-of-user-trust-and-team-perfo/) · [机构 PDF](https://pure.tudelft.nl/ws/portalfiles/portal/245859632/3706598.3713218.pdf)
3. **When Should Users Check?**：最后研究何时检查。它给出检查、找错、修正、重做的成本模型，但当前只优化时间，不是权限或安全引擎。适合为可重做的内部整理工作设计对照；不能据此跳过外发前的必要授权。[固定 v3 原文](https://arxiv.org/html/2510.05307v3) · [PDF](https://arxiv.org/pdf/2510.05307v3)

这三篇不是互相替代：P01 提供参与方式，P02 检查参与是否有效，P03 研究检查时机。它们没有证明我们的动态边界方案优于其他设计。

## 准备落实的设计问题

以下是**本项目提出的待验证假设**，不是论文已验证的结论，也没有在本轮实现新的运行时能力。

| 候选问题 | 可操作对照或反例 | 必须记录，不以点击率代替 |
| --- | --- | --- |
| 共驾是不是只剩审批？ | C 口径由人修正，A/B 保留；比较只给批准按钮与可见的步骤责任/修改范围 | 用户是否知道谁负责下一步、哪些成果不重做 |
| 展示计划是不是制造了放心感？ | 流畅计划中植入一个可从原文定位的错数，同时放入无错误任务 | 漏错、改对为错、主观信心分别记录 |
| 检查点是不是放错位置？ | 同一内容分别在早期、末期出错，另设无错误轨迹 | 检查、诊断、纠正、重做四段时间与独立发现错误情况 |
| 更多解释是否反而阻碍工作？ | 当前对象已定位时允许收起说明；再把指导图与界面版本做错配 | 是否找到正确字段、是否操作错误对象、是否依赖主持提示 |
| 澄清答案是否被当作授权？ | 已给收件人和周期后不再重复问；中途改为仅保留内部草稿 | 新目标是否覆盖旧目标、是否仍错误准备外发 |
| 局部重试是否真的局部？ | 修正 B，比较新旧版本与 A/C 状态 | 修正是否采用、依赖是否清楚、是否将重置误认成撤回 |

建议把这些作为 [现有形成性理解协议](../../comprehension-protocol.md) 的候选补充，而不是直接修改其成功阈值。正式招募前冻结所用版本、任务、顺序和判定条件。先记录第一回答，再允许解释；把新人首次理解与受训后操作分开。

## 核验边界

- 本次六项均打开了作者、机构或固定 arXiv 原文；阅读是有范围的定向核验，不冒充六篇全文精读。
- Cocoa 按 CHI 2026 作者版讨论，不混用 2024 首稿；确认频率论文按 arXiv v3 讨论，其出版 DOI 页获取失败。
- 原文样本、方法和结果的证据类型见 JSON；不搬用未经逐表审核的性能百分比，不把主观评分写成用户理解率。
- 未运行论文代码、训练、付费模型、Runtime、外部业务动作或目标用户测试；未访问被浏览器策略限制的本地 HTML。

当前应交付的是“有依据的设计候选 + 能推翻它的用例”。系统测试通过，只说明对应状态合同；用户有没有看懂，仍须由未参与设计的真实办公人员来回答。
