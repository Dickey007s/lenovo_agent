## 再看三个工程参照

- **E01 [Magentic-UI 官方介绍](https://www.microsoft.com/en-us/research/blog/magentic-ui-an-experimental-human-centered-web-agent/)**：把共同计划、执行中参与、动作审批分开，适合拿来检查我们的交互是否只剩批准按钮。该篇发布博客的主要量化评估使用模拟用户，不能当成真人办公收益。[项目源码](https://github.com/microsoft/magentic-ui) 只是进一步阅读入口，本轮未安装或运行。
- **E02 [Claude Code auto mode 的实现与限制](https://www.anthropic.com/engineering/claude-code-auto-mode)**：重点读“先前批准的覆盖范围”与“子 Agent 收到谁的指令”。这是编程工具内部数据和权限分类实践，不是办公共驾用户研究，也不意味着我们应启用免审批模式。
- **E03 [Agent 评估方法](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)**：把助手说成功、执行轨迹、环境实际结果分开。适合检查测试是否只验证了界面文案；全拒绝、全打扰也不能因没有越界就算成功。

## 对三个 Demo 的设计建议

以下是项目推论，均需再验证，不是论文直接给出的产品结论。

| Demo | 下一步应突出什么 | 用户必须能回答 | 当前没有实现的部分 |
| --- | --- | --- | --- |
| Demo1：跨轮连续任务 | 修改后接着做，不丢失已完成内容 | 我改了哪一步？哪些结果还有效？ | 通用共同计划编辑、任意中间成果合并 |
| Demo2：多 Agent 协作 | 责任、依赖和贡献是否采用，而不是消息数量 | 谁在做？谁被阻塞？修改影响哪些下游？ | 通用权限委派与分布式 Worker，不从 Controller 文本推导用户授权 |
| Demo3：人机边界 | 按具体问题给澄清、批准、纠偏、暂停或查回执 | 我这次决定了什么？还有什么没发生？ | 实际 Connector、外部执行/对账和撤回能力 |

优先推进一个小对照：A/B 已完成，C 的统计口径由人修正，再继续汇总。比较仅给批准按钮与显示责任、修改范围的方式；同时放入“本来正确，不需要人改”的任务。不要先堆一个大型计划编辑器。

## 怎样避免研究只停在推荐列表

已整理 [五组成对设计用例](design-pairs.md)：许可与不许可、需要检查与无需打扰、歧义与无歧义、局部影响与依赖传播、第一理解与受提示后操作。它们是下一轮候选试验，不是新增已通过的五项自动化。

当前八情境原型只覆盖其中有限的状态变化。共同计划、真实依赖变更与委派权限尚未实装；[形成性理解协议](../../comprehension-protocol.md) 也尚无参与者数据。现有研究页增加本地筛选、搜索、推荐顺序和可展开的证据限制，避免把论文结论和设计假设混在一起。
