# 动态边界：研究驱动的交互设计草案

日期：2026-09-11。状态 `Draft`。这是可交互离线原型，不是已接入产品的 Demo3 引擎。

## 1. 不预设等级，先明确约束与事件

旧 L0-L5 提醒我们关注风险与动作，但不能限定未来答案。将它改名成 R0-R3 同样不能解决以下问题：依据不确定不等于权限不足；人确认了不等于动作已经执行；一个低敏感动作也可能违反明确禁止；有审批不等于人在有效监督。

本轮建议比较三种控制方式，而不是先断言其中一种更先进：逐动作确认、有界授权加异常停靠、粗粒度常驻规则。候选方案的要点是**授权一个明确的工作范围，持续检查边界变化，对不同问题给不同的人机分工**。

研究依据与反证见 [findings.md](research/findings.md)。不从来源数量、框架 API 或原型完成度推导产品效果。

## 2. 有界授权的最小设计

需要共同考虑五组事实，但不压成总分：

| 事实 | 问题 | 前台交互 |
| --- | --- | --- |
| 权限与范围 | 谁允许 Agent 对哪些对象做哪些动作，有什么禁止事项？ | 一次具体范围的授权摘要；禁止条件不可被确认覆盖 |
| 信息与依据 | 是否缺必要输入，是否有多种合理解释？ | 请求补充/选择口径，而不是要求“批准不确定性” |
| 影响与恢复 | 影响哪些人、数据和系统；能撤销还是只能补偿？ | 动作差异预览与后果；不把补救当完全撤回 |
| 决定有效性 | 对象、内容、策略或时间是否变化？ | 过期/变更说明、重新核对，无隐式续期 |
| 执行事实 | 未提交、已知成功、已知失败还是结果未知？ | 未知先对账，不能盲重试或伪造取消 |

原型的单次确认绑定动作类型、对象、文件、内容修订、策略版本和外部范围。5 分钟是测试用示例有效期，不是产品建议阈值。真实实现还必须绑定身份、Task/Branch、来源修订、批准内容、执行次数、幂等身份等，不能只用浏览器字符串做安全保证。

## 3. Loop / Swarm 如何共享控制

这是未来接口设计，不是当前实现事实：

```text
用户的任务范围与禁止事项
  -> Controller 提议工作和具体动作
  -> 服务端分别检查权限、依据、影响、决定版本和执行事实
  -> 授权内推进 / 内容澄清 / 动作核对 / 阻止 / 接管 / 对账
  -> 只恢复批准的分支及必要依赖
  -> 新成果与动作回执分开归档
```

Demo1 承接持续任务和局部恢复；Demo2 的每个工作包继承范围但不能扩大权限；Demo3 展示上述边界发生变化时的控制方式。不能把多人、多 Worker 的可视图当成共同授权，更不能通过层层委派稀释原始限制。

## 4. 八种可操作情境

| 情境 | 初始事实 | 操作与预期 | 必须阻止的错误 |
| --- | --- | --- | --- |
| 对外发送 | 对象/版本明确，尚未确认 | 无预选；确认后仍未提交；再模拟提交一次 | 自动发送、重复提交 |
| 授权内整理 | 已允许整理草稿副本 | 直接显示模拟整理结果、原件保留 | 每步无意义审批、冒充真实写入 |
| 依据有歧义 | 全样本与引导后样本口径不同 | 无预选，采用一项并保留限定 | 混用百分比、取得外发权限 |
| 承诺超权限 | 组织/任务禁止越权承诺 | 仅保留草稿或取消 | 确认覆盖禁令 |
| 确认后变化 | 旧确认与新附件不一致 | 再确认；再次更新版本后又失效 | 偷用旧确认 |
| 确认过期 | 模拟时钟超过授权时限 | 重新核对，等待不自动延长 | 默认同意、永久授权 |
| 回执丢失 | 已有一次提交尝试但结果未知 | 查询同一次回执，尝试数仍为 1 | 重复外发、未知冒充失败 |
| 主动接管 | C 暂停，A/B 成果已保留 | 交还后仍需单独授权外发 | 接管删成果、交还即发送 |

“情境变化”提供更换收件人、更新附件、更新策略、时间前进、下一次丢回执。它们是明确标识的故障注入，不伪装成后台真实事件。

## 5. 反证与替代方案

2026 年 Permission Policies 预印本对三种完整界面做模拟办公实验。用户自定义常驻规则减少运行时提示，却没有带来更强越界保护；总干预时间计入规则设置后也不可靠更低。其样本补招和完整界面对比限制了因果拆分，不能将其结果解释为单独否定“有界授权”。

Anthropic 的使用观察也不能反过来证明减少逐步审批必然更安全。两者研究任务、样本、监督条件与指标不同。真正应测试的是：人在关键时刻有没有足够上下文、有权且有能力介入，而不是“点过确认”或“提示少”。

因此本轮不提供风险总分、不承诺最少打扰、不提供永久自动批准开关。逐动作确认仍是应当认真比较的基线，不作为故意设计很差的对照组。

## 6. 待开展的用户对照

- 同一任务池与后果预览，包含正确动作、越权动作、信息缺失、审批过期和未知回执；不要只测异常，也要测正常工作是否被错误拦下。
- 先比较逐动作确认与候选方案，必要时加入粗粒度规则组。记录完整授权配置时间、学习时间与运行时干预时间。
- 控制任务顺序与训练材料；顺序平衡，避免同一人记住同一题答案。样本量、分配方式和分析计划在招募前确定。
- 主要安全指标是越界误放行，另记录合法动作误拒绝、决定对象理解、恢复正确性、总用时、核验行为及工作负担。
- 未制定可接受非劣效界值前不声称效率足以交换风险。角色差异、漏报、长期规则漂移与审批疲劳需要单独观察。
- 所有高影响任务在无外部副作用的模拟中测试；不能为做对照解除真实权限限制。

## 7. 工程落地前的缺口

尚未实现：服务端权限/签发与原子消费、可靠身份、Connector 幂等与对账、真正的异常检测、并发竞争、跨重启恢复、真实撤销/补偿，以及任务特定的风险阈值。当前模型截断内容的问题仍开放；本设计不会让未完整读取的结论变正确。

安全实现与人因有效性必须分别验证。离线 JS 测试只证明被测合成状态转换，不是安全证明。本次测试和截图见 [verification.md](verification.md)。

## 8. 2026-09-12：先让用户看清本次发生了什么

工作面改用 `presenter.js` 从合成状态生成业务表达：先看当前稿和邮件是否发出，再看具体原因与下一步后果。邮件正文不再塞入初始异常说明，避免状态已更新但说明仍过期。附件/收件人/规则变化显示前后值；内容选择保留准确数字和限定，不把“已采用数据”混同“批准发送”。

“接管”改成暂停当前处理，不暗示存在人工编辑器；继续处理后仍需单独确认。保留内部草稿不会删除未经批准的承诺，警告持续显示。测试设置可选择查到已发送、查询失败、没有查到记录，后二者均维持未知，不增加发送尝试。

移动情境入口收为原生下拉，把阅读空间留给当前任务；大多数技术参数进入折叠测试设置。新增 [理解测试协议](comprehension-protocol.md)，先听用户复述，分开记录独立理解、帮助后理解和关键误解。以上仍为待检验的设计假设；不是已完成用户研究或最终视觉验收。
