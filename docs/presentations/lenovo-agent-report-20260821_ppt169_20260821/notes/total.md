# 01_cover

这次汇报先不从模型参数或调用次数开始，而是从一个业务问题开始：Agent 做了事情之后，企业还需要知道什么。客户经理要整理客户 A 的经营信息并准备下一步动作，真正困难的不是得到一段摘要，而是不知道它改了什么、依据是什么，以及下一步会不会产生副作用。我们目前有固定场景的运行证据，但“这套方式已经带来用户价值”仍然是 Draft。这里可能首先会被问到“什么是业务后果”，我的回答是，它不是模型说了什么，而是材料、版本、审批和外部动作实际改变了什么；接下来先看主流方案已经解决到哪里。

---

# 02_mainstream_gap

先把比较的语气放稳：OpenClaw、Codex 和 Claude Code 都在增强执行、并行、权限或恢复能力，我们并不是在这里做性能排名。它们主要让用户看到 session、thread、command 或 diff，而 Office Agent 试图把用户看到的对象换成 Task、Branch、Artifact、冲突和执行回执。这个差异来自官方材料与源码审计，但没有正面对照基准，所以主流差异仍是 Draft，不能说竞品做不到。大家可能会问，为什么不能直接沿用执行框架，答案是企业要追问业务事实，下一页就是这个事实边界。

---

# 03_business_facts_architecture

这张图把主语从“Agent 说了什么”换成“业务事实是什么”：用户工作区提供材料，Runtime 负责任务、上下文、执行和工件，Policy、Evidence、Approval、Permit 与受控工具负责动作边界。自然语言可以提出建议，但身份、来源、版本、风险和结果必须由服务端拥有，前台只投影可读事实，不展示 Prompt、思维链和底层日志。这个分层已经落在当前协议和固定纵切实现里，但把它扩展成完整产品差异仍是 Draft。接下来我们把这套边界拆成八个模块，看看哪些已经有证据、哪些还只是设计目标。

---

# 04_eight_modules

八个模块不是为了把架构画得更复杂，而是把持续运行、上下文、执行、验证、控制和追踪各自放到可检查的位置。固定客户 A 的 Demo 1 和 Demo 2 路径可以标为 Limited Verified，协议与治理已经实现；而跨实例恢复、通用化和生产化仍然明确放在 Draft，不能从固定纵切外推。用户实际看到的不是模块名称，而是每个 Snapshot、Event、Artifact 或 Receipt 对应的业务状态。可能有人会问，模块这么多会不会增加交互负担，所以我们先回到用户真正想完成的一项工作，再看工作区如何承接它。

---

# 05_user_workflow

用户说的是“整理客户 A 经营汇报，给我可确认的下一步”，而不是“请调用几个模型”。现在的代价是往返邮件、CRM、日历和文档，再靠聊天摘要记住来源和版本；目标流程则是读取允许来源、形成草稿、经过冲突与证据门、得到可交付物，最后才进入受控动作。这个工作流和编辑期间不覆盖新输入的交互不变量已经有实现证据，但是否真的降低理解成本或带来效率提升，还没有用户研究，因此价值结论是 Draft。下面用 Demo 1 看一项长任务如何在冲突出现时继续推进。

---

# 06_demo1_durable_task

Demo 1 展示的不是一次回答变长，而是同一个 Task 从 v1 合同、v2 运行，到计划、执行、验证、等待决定，最后进入 v7 提交。客户 A 的关账文件和销售预测文件对收入口径不一致，系统不会替用户自动选择，而是只暂停经营分析分支，同时保留已经验证的风险页和未发送的客户回复草稿。这个固定客户 A、项目仿真文件、文件校验和渐进阶段组成的路径是 Verified，但通用的后台持久 Runtime 仍未被证明。下一页把问题再推进一步：这些“处理中”和“等待决定”究竟由什么服务端事实产生。

---

# 07_ui_server_facts

这里要特别强调，“正在处理”不是动画做出来的，而是 Task 或 WorkCockpit Snapshot、Branch、Worker、ArtifactVersion、Verification 和 Receipt 的协议投影。GET 负责全量对账，SSE 负责有序变化，版本、序列、digest、message_id 和幂等键共同防止重复或晚到事件把界面带偏；缺少事实时，前台只显示状态待核对。当前固定路径属于 Limited Verified，跨进程 SSE、多实例通知和后台队列仍是 Draft。带着这个前提进入 Demo 2，先看用户选择路线之后为什么还不能算任务已经执行。

---

# 08_demo2_controlled_execution

这里请先停一下：画面中的“已选择，尚未启动”不是等待动画，而是服务端明确记录的状态。只有用户确认本轮路线并发出显式启动，系统才创建受控 Execution Snapshot，冻结来源和预算，然后启动三个初始 Worker；收入冲突出现后才增派核对单元，最终共享包完成核验且没有外部副作用。这个结论是固定客户 A、单 API 进程 memory 和四次 deepseek-v4-pro 输出被采用范围内的 Limited Verified，不代表通用 Swarm 或生产队列。大家可能会问，新增的工作单元为什么出现，下一页沿着有序事件解释这次动态重排。

---

# 09_demo2_dynamic_replan

前八个事件是收入事实、项目风险和客户要求的初始并行处理，真正的转折在 seq 9：两份文件的收入字段口径不一致，服务端记录了动态重排。紧接着 seq 10 增加收入定义核验工作单元，去区分已实现收入和预测收入，seq 11 到 14 让共享工件逐步收敛，seq 15 才形成四个 Worker、五个 Artifact 的完成回执。这个事件序列和截图 manifest 可以复核，但四次模型调用的耗时只是本次观察，不能写成生产 SLA；Worker 内部对话也不进入业务界面。接下来再看这些 Worker 如何通过共享工件交接，而不是靠聊天互相转述。

---

# 10_shared_artifacts

多 Agent 的交接单位不是一段难以追踪的聊天，而是带来源、版本、digest 和验证状态的 Artifact。父工件是客户 A 的可验证经营汇报包，收入事实、项目风险和客户回复各自保留来源、版本与 passed 状态，冲突只影响依赖分支，已经验证的工作继续保留。固定路径的共享工件证据属于 Limited Verified，通用跨 Worker 一致性和分布式存储仍然是 Draft。用户接下来可以决定是否进入动作治理，而不是被默认带入发送流程。

---

# 11_demo3_impact_gate

Demo 3 先把动作的具体后果摊开，再让用户决定是否批准：会改变的是由当前已验证工件重建的客户回复发送动作，会重新核对的是证据、风险、权限和绑定版本，已完成的 Task、Artifact 与 Commit 保持不变，真实邮箱、CRM 和 OA 写入不会发生。预演只说明计划发生什么，执行回执才说明实际发生了什么；内容变化、参数不一致、证据不足、拒绝或 Simulator 失败都必须 fail closed，不能回滚已经验证的工作。固定 reply_draft 到 email.send 的 Simulator 动作账本是 Verified，但真实 Connector、生产身份和跨进程 Permit replay 尚未验证。大家可能会问，这些保证如何避免前后端各自解释，下一页直接对照界面字段和服务端事实。

---

# 12_front_backend_contract

这页是一个很朴素但很硬的约束：前端展示什么，后端就必须能证明什么。任务栏回指 TaskSnapshot，分支和冲突卡回指 Branch 与 ConflictRecord，共享工件回指 ArtifactVersion 和验证报告，待确认动作回指 ControlEvent 与 Approval，结果横幅回指 ExecutionReceipt；版本、digest、expected version 和 idempotency 负责把状态变化锁住。这个协议映射是当前工程不变量，但把它推广到所有业务场景仍是 Draft，所以前端不能自行补造秒完成、旧金额、风险、Permit 或模型调用事实。沿着这套共同语言，下一页把三个 Demo 放回同一个 Runtime 里看。

---

# 13_three_demos_one_runtime

三个 Demo 不是三套互不相干的产品：Demo 1 处理时间连续性，Demo 2 处理复杂任务组织，Demo 3 处理业务副作用控制，共同使用 Contract、State、Context、Execution、Capability、Evidence、Policy 和 Trace。用户在不同工作区看到的虽然是阶段与冲突、路线与 Worker、影响预演与回执，但背后都回到来源、版本、事件和用户控制。三个固定纵切分别有对应运行证据，把它们统一成一套完整产品体验仍是 Draft。下一页不再讲结构，而是把已经证明、受限证明和待实验的范围逐项读清楚。

---

# 14_evidence_boundary

这一页请按三种状态来读。Verified 是 Demo 1 的文件冲突路径和 Demo 3 的 Simulator 动作账本，能陈述固定客户 A 路径可运行，也能明确外部真实写入未发生；Limited Verified 是 Demo 2 的固定客户 A、单 API 进程 memory、四个被采用的模型输出和十五个有序事件；Draft 则包括主流差异、通用 Swarm、真实 Connector、成本质量效率、用户价值以及生产恢复。换句话说，不能把 Verified 说成生产可靠性，不能把 Limited Verified 说成分布式 Worker 或 SLA，也不能把 Draft 说成已经实现或竞品做不到；问题是我们下一步怎样把 Draft 变成证据，答案就是四路由对照实验。

---

# 15_four_route_experiment

下一步先冻结同一个客户 A 任务、同一组允许来源和同一模型条件，只改变 Tool Call、Single Agent、Fixed Workflow 与 Adaptive Swarm 四种路由策略。我们比较的不是谁的故事更好听，而是工件完整度、冲突恢复正确率、收敛时间、模型调用数、人工确认负担以及失败或未知结果率，并保留负面结果，把模型能力和编排效果分开。现在这张表只是 Draft 的 planned study，没有任何对照结果，也不应提前许诺成本节省或用户收益。这里可能会被问“为什么选这六类指标”，因为它们分别覆盖交付质量、恢复正确性、资源开销、时间和人的控制负担；最后一页请大家决定是否批准这轮证据生产。

---

# 16_next_evidence_loop

最后的请求不是扩大 Agent 数量，而是批准下一轮“证据生产”：先固化四路由对照，再补齐失败、预算、局部暂停和跨进程恢复，然后开展至少五人的无引导理解测试，最后只把通过验证的共享工件桥接到 Demo 3。这个路线是 Draft 的 next gate，不是生产承诺；每一步完成后都要重新说明场景、来源、前台状态、服务端事实、验证证据和边界。我想请大家确认的不是一句“看起来不错”，而是是否同意用这四个门把“Agent 做了什么”逐步收敛成“工作实际发生了什么”。
