## 二、场景一：跨日经营简报，冲突只暂停一条工作线

### 建议页标题

**跨日经营简报：有一处口径冲突，不必整份报告重来**

### 用户、触发和目标

- 用户：需要在次日经营会前完成客户经营简报的业务负责人、项目经理或财务分析人员。
- 触发：客户、项目、正式财务和预测资料分散在不同文件中；正式收入为 2,400 万，预测口径为 2,680 万。
- 用户原话示例：

> 根据资料库完成本季度经营简报。正式收入作为当前口径，预测数据保留差异说明；所有结论都要能回到原文。

- 完成条件：简报可下载；客户事实、项目风险和收入结论都有来源；收入冲突已经由用户明确处理；旧成果和旧版本仍可查看。

### 页面上只画这一条主流程

```text
整库查找资料
    -> 客户事实 / 收入口径 / 项目风险三条工作线
    -> 发现 2,400 万与 2,680 万冲突
    -> 只暂停“收入口径”
    -> 用户选择“正式口径 + 保留预测差异”
    -> 只恢复这一条，生成简报新版本
```

### 用户在前台看到什么

- 已完成：客户事实、项目风险继续保留，不显示成“整个任务失败”。
- 需要我处理：并排显示两种口径、各自来源、影响和选择后果。
- 确认之后：只恢复收入工作线；旧简报仍可查看，新简报形成新版本。
- 交付结果：简报、来源入口、校验记录和任务历史分开呈现。

### 为什么这样设计

| 设计选择 | 依据 | 相关性 | 不能据此声称 |
| --- | --- | --- | --- |
| 任务状态可保存并从中断处继续 | [LangGraph Persistence](https://docs.langchain.com/oss/javascript/langgraph/persistence) | Checkpointer 保存线程状态，支持连续对话、人工介入、故障恢复和状态回看 | 不能证明本项目的业务分支和成果版本自动正确 |
| 需要人判断时暂停，决定后继续原任务 | [OpenAI Agents SDK Human-in-the-loop](https://openai.github.io/openai-agents-python/human_in_the_loop/) | 工具调用可进入待审批中断，`RunState` 可序列化并在批准或拒绝后恢复 | 不能证明“正式口径”应该如何选择，也不提供办公证据治理 |
| 错误时应支持局部纠正、歧义时先澄清、解释系统行为并保留近期交互 | [Microsoft HAX 18 条人机交互指南](https://www.microsoft.com/en-us/haxtoolkit/ai-guidelines/) | 对应 G9 纠正、G10 歧义降级、G11 解释原因、G12 记住近期交互 | 不能证明当前页面已经更易懂或更可信 |
| 旧成果不覆盖、只继续目标分支 | [SCENARIO-038](../../../scenarios/SCENARIO-038-durable-task-continuation-across-runs.md) 与 [DR-0053](../../../decisions/DR-0053-durable-task-lineage-and-explainable-topology-admission.md) | 当前系统对任务谱系、分支重核、成果版本和后继执行段的工程约束 | 固定测试不证明任意办公任务正确或生产级恢复 |

### 当前事实与边界

- **当前有限实现：** 同一任务下的后继执行段、分支证据门、成果版本、历史保留、局部恢复和可选 PostgreSQL 顺序恢复。
- **尚未证明：** 任意复杂办公任务都能正确收敛、多实例高可用、跨端长期运行、目标用户理解和业务价值。

### 建议讲稿

这里不是为了证明系统“能跑很多轮”，而是说明复杂办公任务停下来之后，用户不用重开
对话、重讲背景，也不用把已经完成的工作全部推倒。外部运行时资料支持保存、暂停和恢复
这种机制；真正属于本方案的设计，是把恢复范围绑定到业务工作线、来源重核和成果版本。
它目前有工程证据，但用户是否真的更容易理解和纠偏，还需要目标用户测试。

## 三、场景二：跨部门上线核验，先判断是否值得启用自适应协作

### 建议页标题

**跨部门上线核验：不是任务一复杂，就固定启动很多智能体**

### 用户、触发和目标

- 用户：需要汇总产品、质量、运营、法务和发布材料，但不愿管理多个智能体对话的项目负责人。
- 触发：资料跨多个目录，部分工作可以独立核对，另一些工作必须等待前序结论。
- 用户原话示例：

> 分别核对产品上线、搜索智能体运行和用户交互三条工作线，先独立核对，再形成一份统一的风险与待办简报。

- 完成条件：用户知道为什么选择当前路线、哪些工作包实际启动、哪些结果已进入统一成果、单项失败影响什么。

### 页面上先讲四种路线的关系

```text
简单且确定                  -> 直接工具（当前尚未具备通用能力）
单一但需要动态判断          -> 单一智能体循环
步骤固定、前后依赖明确      -> 固定流程
来源跨度大、工作可独立、价值高 -> 受治理的自适应协作
```

这四条不是能力等级，也不是越往右越好。系统先根据独立性、依赖、来源跨度、预算和风险
给出路线；只有高成本的自适应协作需要用户确认。

### 场景主流程

```text
拆成 5 个工作包
    -> 服务端判断独立性、依赖、预算和风险
    -> 用户确认后，首批最多启动 3 个只读执行单元
    -> 每份返回分别核对来源与原文位置
    -> 通过的内容进入成果，失败只影响对应工作包
    -> 形成一份统一简报和下一批待办
```

### 用户在前台看到什么

- 为什么建议这条路线，而不是只显示“已启动多个智能体”。
- 工作包之间谁依赖谁，当前实际启动了几个。
- “已经返回”和“已经采用”明确分开。
- 一个工作包失败时，已有成果继续可用，用户只处理受影响部分。
- 用户审查的是统一成果、例外和下一步，不需要阅读多个智能体聊天室。

### 为什么这样设计

| 设计选择 | 依据 | 相关性 | 不能据此声称 |
| --- | --- | --- | --- |
| 先用最简单路线，只有需要时增加复杂度 | [Anthropic: Building effective agents](https://www.anthropic.com/engineering/building-effective-agents) | 区分固定工作流和动态智能体；强调成本、延迟与可预测性的取舍，并提出编排者-执行者模式 | 不能证明本项目的路线选择一定最优 |
| 多执行单元适合可独立、广度优先的高价值任务，不适合强依赖任务 | [Anthropic: How we built our multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system) | 官方实践披露并行研究的适用条件、协调困难和约 15 倍聊天 Token 的内部数据 | 该成本与效果数字不能外推到本项目 |
| 让一个管理者统一对话和成果，专家只处理有界子任务 | [OpenAI Agents SDK: Agent orchestration](https://openai.github.io/openai-agents-python/multi_agent/) | `agents as tools` 让管理者保留最终回答与共同约束；代码编排可提高确定性 | 不能证明多智能体一定优于单智能体 |
| 任务状态和任务输出应分开表达 | [A2A Protocol Specification](https://a2a-protocol.org/latest/specification/) | A2A 区分任务状态、输入等待、消息和成果对象 | 本项目目前不宣称已经兼容 A2A |
| 先准入、再启动；返回候选先过门再进入统一成果 | [SCENARIO-041](../../../scenarios/SCENARIO-041-workunit-contribution-ledger-and-partial-convergence.md)、[DR-0055](../../../decisions/DR-0055-durable-workunit-and-contribution-ledger.md) | 当前系统已有五工作包、依赖波次、候选采用、部分成果和恢复台账 | 不能证明远端调度、分布式执行或质量收益 |

### 当前事实与边界

- **当前有限实现：** 服务端路线准入；每批最多三个进程内只读执行单元；工作包依赖、候选贡献、采用门、部分成果和新成果版本。
- **尚未实现：** 远端执行单元、持久队列与租约、多实例协调、递归扩容、真实跨应用连接器。
- **尚未验证：** 自适应协作是否比单一流程更快、更便宜、更正确；这必须同任务、同模型、同来源、同预算比较。

### 建议讲稿

这一页要把单一流程、固定流程和自适应协作的关系说清。简单查证不该为了展示技术而
启动多个智能体；步骤可预先确定时，固定流程更稳定；只有工作包确实能独立、来源跨度
大、任务价值足以覆盖协调成本时，才建议自适应协作。外部实践支持这种取舍，但本项目
还没有性能优势证据，因此只能说“路线准入和有限协作已经实现”，不能说“协作一定更好”。

## 四、场景三：客户外呼流程，方案完成不等于动作已经发生

### 建议页标题

**客户外呼流程：文件可以先完成，真实动作必须另行审批**

### 用户、触发和目标

- 用户：需要根据内部制度设计外呼流程的运营负责人或合规复核人员。
- 触发：制度文件规定身份确认、录音告知、联系时段、频次、第三方处理和转人工条件。
- 用户原话示例：

> 根据制度生成客户外呼流程，标出需要人工审批的节点，并说明这次到底执行了什么。

- 完成条件：来源规则可回查；流程文档可下载；规则覆盖和图结构已检查；审批状态和真实动作状态不混在一起。

### 页面上的五段事实链

```text
读取制度
    -> 生成外呼流程文档
    -> 校验规则覆盖和图结构
    -> 展示影响并等待人工审批
    -> 只有未来具备连接器、许可和执行回执后，才能声称动作发生
```

### 用户在前台看到什么

- **已完成：** 外呼流程文档已经生成，来源与结构检查通过或失败。
- **待决定：** 最终合规审批尚未发生。
- **明确未发生：** 未拨号、未写客户系统、未发短信、未写禁呼名单、未实际转人工。
- 未来若接入真实动作，确认页必须先显示对象、范围、风险、可逆性和执行后果；执行后再显示可核验回执。

### 为什么这样设计

| 设计选择 | 依据 | 相关性 | 不能据此声称 |
| --- | --- | --- | --- |
| 敏感工具调用前暂停，批准或拒绝后恢复 | [OpenAI Agents SDK Human-in-the-loop](https://openai.github.io/openai-agents-python/human_in_the_loop/) | 支持按工具与参数决定是否审批，并把批准、拒绝、运行中断和恢复分开 | 不代表本项目已经具备真实外呼工具或生产许可 |
| 向用户说明谁在请求、为什么请求，并提供接受、拒绝和取消 | [MCP Elicitation](https://modelcontextprotocol.io/specification/draft/client/elicitation) | 协议要求清楚说明请求方和用途，允许用户检查与修改输入，并区分接受、拒绝、取消 | MCP 仍不规定完整产品界面，也不替代业务授权 |
| 歧义时先澄清、错误时可纠正或撤销、解释系统为什么这样做 | [Microsoft HAX 指南](https://www.microsoft.com/en-us/haxtoolkit/ai-guidelines/) 与 [Google PAIR Feedback + Control](https://pair.withgoogle.com/guidebook-v2/chapter/feedback-controls/) | 支持在人和自动化之间保留控制，明确反馈会怎样影响系统 | 不能证明当前审批界面已通过目标用户验证 |
| 文件成果、业务审批和真实动作分层 | [DR-0047](../../../decisions/DR-0047-tc10-source-derived-outbound-flow.md) | 当前固定场景已把文档校验、审批状态和 `external_action=none` 分开 | 不能声称已外呼、已写系统、已获法律意见或适用于任意制度 |

### 当前事实与边界

- **当前已实现的固定纵切：** 从批准来源推导规则、生成流程文档、校验来源覆盖与图结构，并明确记录没有外部动作。
- **目标能力：** 真实连接器、身份授权、动作许可、幂等执行和外部系统回执。
- **禁止表述：** “流程节点已经执行”“文件检查通过等于业务批准”“系统已经具备生产外呼能力”。

### 建议讲稿

这一页解决办公智能体最容易误导用户的问题：方案、文件、审批和执行不是同一件事。
当前系统可以生成并校验流程设计，但必须把未发生的拨号、写系统和短信放在首屏。人工
审批与执行回执的设计有成熟 SDK、协议和人机交互原则可参考；但在真实连接器和权限链
出现前，这一页必须停在“方案已形成、动作未发生”。

## 五、单独一页说明：这些依据分别能证明什么

### 建议页标题

**方案不是来自单一论文：四类依据共同约束，但证明范围不同**

| 依据类型 | 具体材料 | 对方案的作用 | 当前结论边界 |
| --- | --- | --- | --- |
| 竞品实践 | [ChatGPT 深度研究](https://help.openai.com/en/articles/10500283-deep-research)、[Microsoft 365 Copilot Researcher](https://learn.microsoft.com/en-us/microsoft-365/copilot/researcher-agent)、[Codex App](https://openai.com/index/introducing-the-codex-app/) | 说明来源选择、计划审阅、进度、中断、引用报告、并行任务、隔离和审查已经成为市场预期 | 只能定义主流基线，不能从公开页面推断竞品做不到其他能力 |
| 工程框架与协议 | [LangGraph Persistence](https://docs.langchain.com/oss/javascript/langgraph/persistence)、[OpenAI HITL](https://openai.github.io/openai-agents-python/human_in_the_loop/)、[OpenAI Orchestration](https://openai.github.io/openai-agents-python/multi_agent/)、[MCP Elicitation](https://modelcontextprotocol.io/specification/draft/client/elicitation)、[A2A](https://a2a-protocol.org/latest/specification/) | 说明检查点、人工介入、协作编排、结构化追问、任务状态和成果对象如何落地 | 证明机制可实现或正在标准化，不证明本项目体验更好 |
| 人机交互研究 | [Microsoft CHI 2019 研究](https://www.microsoft.com/en-us/research/publication/guidelines-for-human-ai-interaction/)、[HAX 设计指南](https://www.microsoft.com/en-us/haxtoolkit/ai-guidelines/)、[Google People + AI Guidebook](https://pair.withgoogle.com/guidebook-v2/chapters) | 约束能力边界、解释、纠错、歧义处理、反馈与控制、优雅失败 | 是通用研究与方法，不是本项目的目标用户结论 |
| 当前工程实践 | 当前 Decision、Scenario、自动化、真实成果文件、服务端状态与 PostgreSQL 顺序恢复记录 | 证明固定公开资料和限定边界内，哪些状态、成果与恢复行为已经存在 | 不证明任意任务正确、生产稳定性或用户价值 |

### 必须公开写出的缺口

**当前没有正式目标用户研究。** 现有反馈来自项目 Stakeholder、截图审阅和工程自动化，
足以发现问题和约束修订，但不能代表财务、项目、运营或合规用户群体。

建议下一轮先做 5 至 8 人形成性任务测试，不追求统计代表性，先验证三个核心任务：

1. 能否在无讲解下说清“已经完成什么、哪一条为什么暂停”；
2. 能否找到支撑结论的原文，并理解点击确认只影响哪一部分；
3. 能否区分“文档已生成、模型返回、业务已批准、外部动作已发生”。

建议记录：状态理解正确率、证据回开成功率、恢复步骤与耗时、误把未执行动作当成已执行
的比例、被打断次数和主观控制感。指标组织可参考
[Google HEART](https://research.google/pubs/measuring-the-user-experience-on-a-large-scale-user-centered-metrics-for-web-applications/)，
但样本、任务和统计方法确定前，不对外声称体验提升。

## 六、竞品实践如何进入三页场景，而不是再做一张功能表

### ChatGPT 深度研究

官方资料明确提供来源选择、研究计划审阅与修改、运行进度、中断调整和带引用报告。
因此它是“用户审来源、计划、进度和报告”的市场基线。我们的场景不能把“有来源、能暂停”
写成独占差异，而应验证分支级采用、局部恢复和成果校验是否形成更完整的办公事实链。

### Microsoft 365 Copilot Researcher

官方资料显示它可结合 Web 与用户有权访问的文件、邮件、会议和聊天，形成带来源的复杂
研究报告。这说明原生办公上下文和权限继承是主流强项。本项目当前没有同等级连接器，
只能展示固定资料库中的冻结来源、校验和恢复合同。

### Codex App

官方资料把独立任务、并行智能体、隔离工作区、变更审查和后台自动化放进统一工作台。
它建立了长任务监督的用户预期。我们的候选差异不能写成“也能跑长任务”，而是把办公
来源、业务工作线、成果版本、人工决定和未执行边界放到同一条可核对链路中。
