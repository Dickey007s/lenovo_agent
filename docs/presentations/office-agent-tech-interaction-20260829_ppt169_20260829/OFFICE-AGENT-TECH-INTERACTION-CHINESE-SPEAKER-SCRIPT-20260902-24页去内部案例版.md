## P01 未来办公 Agent：从一次回答到可治理工作系统

建议时长：1.5 分钟

07-16 的第一页讲了四个方向：持续、协作、治理和交付。这个判断今天不变。

持续，不是让一次对话变得更长，而是同一个任务在时间、设备和服务重启之后仍然拥有可恢复的状态。协作，不是为了展示有多少个 Agent，而是复杂任务需要时能够拆分工作，并最终收敛为一套结果。治理，是系统要知道范围、预算、证据、权限和停止条件。交付，则要求最终产物不仅“看起来像答案”，还要说清来源、版本、校验结果和未执行边界。

右侧换成当前 Agent 能力页的真实运行界面。它默认先给任务进展，再按需进入完整执行记录、协作方式和原文核对。固定公开资料仍被组织成 15 个目录、96 份输入文件。它的意义不是数字本身，而是我们已经把抽象架构放进了一个用户可以浏览、搜索、预览、追踪协作并回开原文的办公资料环境。

但这里先划一条边界：这是固定公开数据上的当前系统实测，不是企业生产资料，也不证明用户体验已经改善。

转场：接下来先看 07-16 的三个 Demo 分工，在当前版本里分别落到了什么程度。

## P02 这次版本带来的能力跃迁

建议时长：2 分钟

07-16 把三个 Demo 分成三个治理维度。Demo 1 管时间维连续性，Demo 2 管组织维复杂性，Demo 3 管动作维风险。这个分工仍然保留。

当前版本真正向前推进的地方，是把抽象 Demo 落到了 Workspace 范围、服务端 Branch、证据门、真实成果和未执行边界上。

Demo 1 现在能体现受限的单 Agent Control Loop：服务端冻结任务范围，规划本轮路径，按分支记录证据和缺口，保存逻辑成果版本，并在中断后恢复到检查点。Demo 2 已经形成受控的组织纵切：服务端编译 WorkUnit DAG，按依赖分波，每波最多启动三个进程内只读 Worker，Worker 返回和 Contribution 采用分开记账，再收敛到统一 Artifact；它仍不是分布式 Swarm。Demo 3 还没有真实 Connector 执行动作，不过“方案已经生成”和“外部动作没有发生”能够被明确分开。

这种变化直接影响用户界面。界面不能只告诉用户“Agent 正在运行”或者“任务已完成”，而要进一步说清：为什么停、受影响的是哪条分支、现有成果是否保留、用户确认后会改变什么，以及什么动作仍然没有发生。

转场：这些状态并不是零散文案，它们需要一套稳定架构来负责。

## P03 一个底座、两层增强、三类控制

建议时长：3 分钟

这一页先看三层关系，英文只保留为系统中的正式名称。

最下面是统一任务运行底座。每个任务都要经过它：记住目标和当前状态，为每一步准备上下文，调用允许的能力，保存证据与策略决定，并留下执行记录。没有底座，智能体仍然只是一次模型调用，任务中断后不知道从哪里继续，也无法说明结论或动作来自哪一步。

中间是第一层增强，智能体控制循环（Agent Control Loop）。它只在任务需要多轮推进、等待补证或恢复时发挥价值，解决的是时间维连续性。当前已经落地的是顺序单控制器、服务端分支、分支证据门、追加式成果版本，以及状态快照和有序事件。

最上面是第二层增强，受治理的自适应协作（Governed Adaptive Swarm）。它面向高价值、跨来源、存在明确依赖的复杂工作。当前只完成了一个最小受控纵切：路线准入、工作包依赖图、每批最多三个进程内只读执行单元、贡献采用门和统一成果。持久任务队列、租约、远端执行、多实例协调和通用冲突消解仍是目标，不能把这条纵切讲成分布式协作运行时。

左侧三类控制不是另一组业务模块，而是贯穿所有层的约束。Task Control 决定目标、范围、预算、暂停和停止；Evidence Control 决定来源、冲突、验证以及模型说明是否采用；Action Control 决定风险、审批、Permit 和执行回执。

用户不需要理解这套架构名词。用户最终只需要前台回答三件事：任务现在走到哪，当前结论凭什么成立，哪些动作真的发生了。

转场：下一页把底座拆成八个稳定职责，并说明每两个模块共同回答一个用户问题。

## P04 Agent 最小运行时：八个稳定职责

建议时长：3.5 分钟

八个模块不是八个前台页面，而是一次任务从定范围到可恢复的四段责任链。

第一段叫定范围。Workspace Catalog & Safe Preview 负责哪些资料可以安全读取，Task Contract 负责目标、范围、完成条件和禁止事项。对应到前台，就是回答“你读了哪些资料、任务边界是什么”。

第二段叫定计划。Planner 可以提出分支、依赖和资料范围，但模型返回的计划不能直接运行。Admission、Policy Compiler & Plan Validator 还要校验预算、来源、依赖、工具和副作用。对应到前台，就是回答“为什么这样拆、什么计划被拒绝或修复”。

第三段叫推进执行。Scheduler & Worker Manager 决定哪个分支先做、依赖谁、何时等待、何时恢复；当前已经支持服务端 WorkUnit DAG、显式波次与每波最多三个进程内只读 Worker。Tool Gateway 应统一真实工具的授权、超时、幂等和回执，但当前仍是目标。对应到前台，就是回答“现在做到哪一步、谁依赖谁、哪个分支受影响、动作是否真的执行”。

第四段叫成果恢复。Artifact Workspace & Verifier 保存成果版本并执行当前固定场景的确定性检查；Checkpoint, Event & Governance Control 让 Snapshot 成为状态权威，SSE 只做有序投影，并提供可选 PostgreSQL 重启恢复。对应到前台，就是回答“结果能否下载、核对、审计和恢复”。

所以模块对后端是职责，对用户只有四个问题：读什么、怎么做、做到哪、结果能不能复核与恢复。蓝色表示当前实现，橙色表示部分近似，灰色表示目标，不能把目标模块写成现有能力。

转场：这些职责为什么会逐步出现，可以沿着技术工程对象的变化来看。

## P05 技术演进：工程对象不断外扩

建议时长：2 分钟

这页把 07-16 的五页技术演进合并成一条链。

Prompt Engineering 的核心对象是一次指令和少量示例，重点是让单次输出可用。ReAct 把工程对象扩展到 Action 和 Observation，让模型能够根据环境反馈继续行动。Context Engineering 再把系统指令、工具、外部数据和历史状态作为一个整体管理。Harness Engineering 把权限、沙箱、工具环境和调用边界纳入系统。Loop Engineering 是我们对触发、验证、记录、恢复和再次触发的工程归纳。

最后落到办公交付，系统需要同时管理业务成果、来源、人工决定和未执行边界。真正的变化不是“模型突然变成 Agent”，而是系统逐步接管了更多责任。

需要提醒，这些阶段名称不是学界统一年表，尤其 Loop Engineering 是本方案用于解释责任扩展的归纳。论文和官方实践可以支持这条技术脉络，但不能单独证明我们的实现更先进。

转场：理解完技术演进，下面不按功能打勾，而按用户实际审查的对象看主流方案。

## P06 先分赛道：直接竞品、邻近工具与底层方法不能混比

建议时长：2.5 分钟

原来的竞品页把商业产品、执行工作台和底层方法放在同一层，容易得到错误结论。这一版先分五条赛道。

第一条是办公套件内嵌，代表是 Microsoft 365 Copilot 和 Google Workspace with Gemini。第二条是企业知识与智能体平台，包括 Glean、Atlassian Rovo 和 Notion AI。第三条是通用研究工作台，包括 ChatGPT 深度研究和 Claude Research。第四条是任务执行工作台，包括 Codex App、Claude Code 和 OpenClaw。第五条是 ReAct、MCP、A2A 这样的底层方法与协议，它们不是完整产品。

这样分层以后，比较对象就从“有没有某个功能”，转向六个连续问题：用户处理什么工作对象，状态怎样保留，证据怎样回开，成果怎样验证，人工何时介入，以及动作到底有没有发生。

本页不是竞品排名，也不因为官方资料没有写某项机制，就推断竞品一定做不到。

转场：先看最直接的办公套件竞争。

## P07 办公套件竞品：优势在原生上下文和真实应用动作

建议时长：2.5 分钟

Microsoft 的优势不是一个孤立的问答框，而是它直接位于 Microsoft 365 的工作内容和权限体系里。Researcher 可以结合工作来源与互联网开展研究，Computer Use 还可以在隔离环境中操作网站或应用，并在动作前请求确认。

Google 的路线类似但产品组织不同。Gemini 理解 Gmail、Drive、Docs 和 Chat 的办公上下文，Workspace Studio 则把跨应用智能体和自动化放进同一工作面。

这对 Office Agent 有两个直接含义。第一，多来源、整库、引用已经不能作为独占表述。第二，Office Agent 当前没有这些原生套件连接，也不会写回源文件或执行真实业务动作。

我们仍可继续验证的，是资料范围、分支证据、模型采用、办公成果和人工决定是否能形成更清楚的事实合同。

转场：办公套件之外，企业知识平台正在把搜索、研究和行动连成一个入口。

## P08 企业知识工作台：全源搜索已经成为日常入口

建议时长：3 分钟

页面用 Notion AI 的官方界面作为可视例子。它把 Notion 页面、数据库、Slack、Drive、Jira 等连接源和互联网放进统一入口；用户可以收窄来源范围，并从回答引用回到原始内容。研究模式处理开放问题，部分连接器还能在连接应用中执行动作。

同一赛道不能漏掉 Glean 和 Atlassian Rovo。Glean 以权限感知的企业搜索和知识图谱为底座，向深度研究、智能体和动作扩展。Rovo 把搜索、对话、深度研究、智能体和自动化嵌入 Jira 与 Confluence，并能在许可下创建或编辑工作项。

所以“企业连接、全源搜索、带引用回答”已经是直接竞品的基线。Office Agent 的候选差异只能继续落到：模型结论是否经过服务端采用，缺口能否只恢复一支，办公成果是否独立校验，以及计划、批准和真实动作是否分开。

转场：再看通用研究产品，用户已经能审查哪些过程。

## P09 跨来源研究：用户已经在审计划、来源、进度与报告

建议时长：2.5 分钟

ChatGPT 深度研究允许用户选择互联网、文件、连接应用和指定网站。研究前可以审查计划，运行中可以查看进度、继续引导或中断，最终报告带引用，并可导出为 Markdown、Word 或 PDF。

Claude Research 也会在互联网和已连接内部资料中开展多步研究，用户可以开关研究模式、补充来源，并检查最终引用。

因此，“有来源、有计划、有进度、可中断、可下载”也是市场基线。Office Agent 若要拉开验证，必须进一步证明业务分支是否有来源准入，模型返回和采用是否分开，成果是否真写出并通过独立检查。

转场：代码任务工作台虽然不是直接办公竞品，但已经建立了长任务审查的用户预期。

## P10 任务执行工作台：用户审“改了什么、验证了没有”

建议时长：2.5 分钟

Codex App 按项目和任务线程组织长期工作，隔离工作树、差异审查、技能、终端和自动化进入同一工作台。Claude Code 围绕项目、终端和版本库运行“收集上下文、采取行动、验证结果”的循环，并提供会话恢复、分叉、检查点和权限控制。

它们不是同一办公资料产品，但已经说明长任务连续、隔离执行、人工审查和验证回执并不新鲜。

Office Agent 要证明的不是“也能跑很久”，而是能否把办公来源、业务发现、证据门、办公成果、人工决定和未执行边界放进一条可复核事实链。

转场：接下来把前面的产品叙事压缩成五个真正可比的审查对象。

## P11 真正该比的，不是功能数量，而是五个可审查对象

建议时长：3 分钟

第一个对象是工作对象。办公套件处理邮件、文档、会议和企业图谱；研究工作台处理网页、文件和连接应用；代码执行处理仓库、终端和任务线程；Office Agent 当前处理冻结资料库、任务、运行和业务分支。

第二个对象是持久状态。市场产品分别以应用活动、自动化流程、研究计划、报告、会话和检查点保存连续性。Office Agent 当前用运行版本与任务版本保护单次控制和跨运行指针，并保存分支与成果历史。

第三个对象是证据。竞品常见来源链接、引用、步骤、差异、命令和测试。Office Agent 当前把文件引用、原文锚点和分支证据门绑定起来。

第四个对象是成果。竞品可以生成文档、消息、报告、代码和自动化。Office Agent 当前只对固定本地能力生成隔离办公成果，并留下独立校验回执。

第五个对象是人工与动作。Office Agent 当前支持选分支、做决定和逻辑回滚，但外部动作仍未实现。

这张表是官方定位和当前实现的结构化归纳，不是同场实测结果。

转场：最后把可以讲的候选差异和不能讲的空白放在同一页。

## P12 Office Agent 的候选差异：不是能力更多，而是证明链更完整

建议时长：3.5 分钟

左侧是当前已有证据。第一，整库索引在运行创建时冻结，计划由服务端编译成稳定分支和路线。第二，发现项必须绑定批准来源与原文锚点，模型已经返回和结果被采用是两个事实。第三，固定本地能力会生成隔离成果，独立校验器给出回执，成果版本与任务提交保留追加式历史。

右侧是仍没有证据。当前没有 Microsoft、Google、Glean、Rovo 或 Notion 的原生连接器，不写回源文件；没有远程执行单元、分布式租约、多实例协调和生产认证；也没有目标用户研究证明效率、信任或业务价值提升。

因此，最准确的表述是“可证伪的合同集成差异候选”，而不是“已经胜过竞品”。下一步固定配置同场实测至少回答四个问题：结论能否定位，暂停后能否只补一支，成果是否真写出，计划、批准和执行是否严格分开。

转场：有了市场基线和候选差异，下面回到它怎样改变具体用户流程。

## P13 技术差异如何逐步改变用户流程

建议时长：2 分钟

第一步，用户先说目标。服务端冻结完整允许范围，而不是让用户提前猜测应该勾选哪些文件。用户因此少做一次文件选择，但系统必须明确告诉他本次任务能读取什么。

第二步，Planner 提议路径，服务端校验预算、依赖、工具、来源和禁止动作。用户看到的不再只是“正在思考”，而是任务分支、当前阶段和为什么不能继续。

第三步，模型调用和模型输出采用被拆成两个事实。`called=true` 只说明模型返回了候选，不代表候选已经成为当前结论。前台需要把被采用、未采用和冲突原因分开呈现。

第四步，证据定位出现多义时，只暂停受影响的 Branch，已经完成的成果和其他分支继续保留。用户不再被迫重跑整项任务。

第五步，Artifact、模型说明和外部动作分层。成果文件通过检查，不等于叙述一定正确；形成方案，也不等于外部系统已经执行。

这些变化分别对应 Workspace-first、服务端策略编译、分支级 Evidence Gate、成果回执和人工门。它们共同把交互从“相信一段回答”，变成“审查当前事实和下一步影响”。

转场：一旦任务进入多轮循环，这些设计还要面对长任务风险。

## P14 长任务 Loop 的风险会被循环放大

建议时长：1.5 分钟

07-16 已经提出六类风险：方向漂移、上下文退化、错误复利、成本扩张、权限漂移和停止困难。

它们在前台分别变成六个用户问题：目标是否仍然一致？当前使用的是哪版来源？预算还剩多少？系统被允许执行什么动作？哪条 Branch 受到影响？我如何暂停、恢复或者接管？

当前系统解决的是其中一部分。控制循环默认 12 轮、公开上限 24 轮，同时受每轮文件数、模型调用次数和主动运行时间的独立预算约束。暂停和停止只会在模型调用之间的安全点生效，也不会硬取消正在进行的请求。因此它还不是无限自治的长任务执行器。

这里也回应“轮数是否够用”的问题：12 轮只是默认预算，24 轮只是公开上限，都不是质量承诺。是否够用仍要结合完成条件、其他预算和固定场景测试判断，而不能只看一个轮数。

转场：下一页具体看当前 Agent Control Loop 已经形成了什么，又缺什么。

## P15 Agent Control Loop：当前实现与缺口

建议时长：2 分钟

中心五段是 Observe、Plan、Act、Verify 和 Commit。

Observe 和 Plan 已经有较清晰的纵切：服务端读取安全索引、冻结范围、规划本轮证据和分支。Act 仍主要是只读分析和固定成果适配器，不是通用执行器。Verify 能做 Schema、引用成员关系、位置定位和部分确定性成果检查，但不能证明自然语言结论全面正确。Commit 是追加式的逻辑 ArtifactVersion 和 TaskCommit，不会覆盖历史成果。

外围控制中，任务约束、证据门和执行记录相对完整；预算、纠偏/暂停和持久状态是有限实现；接管、通用 Tool Gateway、远端或分布式执行单元和外部动作仍缺。当前只有每批最多三个进程内只读执行单元，不能把它写成通用多 Worker 运行时。

历史审计曾给出约 30% 的架构成熟度基线。这个数字只描述当时 11 个模块的等权成熟度估计，不是测试覆盖率，也不是模型质量。现阶段最准确的说法，是一条具备状态、证据门和局部恢复的受限办公任务纵切。

转场：这些系统事实最终要落到前台，让业务用户迅速看懂当前结果、依据和下一步。

## P16 前台交互只需要先回答五个问题

建议时长：2 分钟

第一，现在完成了什么？这里应该优先展示成果文件、确定性检查和当前复核状态。

第二，依据是什么？用户需要看到来源文件、原文位置和可回开的摘录。

第三，为什么停？系统应说明问题本身、影响范围和可恢复动作，而不是只给技术错误码。

第四，我确认后会改变什么？比如只恢复哪条 Branch、是否新增一个成果版本、是否会触发外部动作。

第五，什么绝不会发生？当前只读、未接入 Connector、不会覆盖原始文件等边界应该明确出现。

技术信息并没有因此消失，而是分成三层。首屏是当前结论，放成果、复核状态和未执行边界；展开层解释来源、校验、模型说明是否采用和局部决定；审计层再提供 Snapshot、version、named SSE 和 DecisionRecord。

这页的目标不是把字变少，而是让阅读顺序符合业务判断。现场截图和这几轮反馈只能说明我们发现了理解问题，还不是正式用户研究。下一步应让目标用户在无引导情况下说出当前结果、来源、影响和下一步，并使用 HEART 等框架记录理解、负担和任务成功。

转场：接下来用四页真实界面，把前面讲的系统纵切完整走一遍。

## P17 我们到底做了什么：跑通一条办公任务纵切

建议时长：2 分钟

这页回答最直接的问题：我们到底做了什么。

我们不是又做了一张 Agent 对话页面，而是跑通了从办公资料到可复核成果的一条纵切。第一层是 Workspace：15 个顶层目录、96 份输入文件经过服务端安全检查后进入可预览范围。第二层是 Task Contract：用户写任务目标，服务端冻结可读范围、预算、禁止动作和当前版本。第三层是 Planner 与 Analyst：模型调用、服务端校验、输出采用分别记录。第四层是 Branch Evidence Gate：证据不能唯一定位时，只让受影响分支等待。第五层是真实 Artifact 与回执：固定场景可以生成可下载文件，执行具名检查，并留下 Snapshot 和有序 Trace。

右侧截图展示的是当前系统完成一条固定办公任务后的完整运行界面。左侧是资料库，中间是任务路径和成果，右侧是 Control Loop 记录。它把“目标、资料、计划、核对、成果、回执”放进同一工作面。

当前已经证明的是固定公开数据上的受限纵切；尚未证明的是通用语义正确、任意办公文件写入、生产级 Connector 和生产 SLA。

转场：下一页从用户输入开始，看自主选择资料具体怎样发生。

## P18 实操 1：用户只说目标，智能体自主选择资料

建议时长：2 分钟

用户做的第一件事只有一个：写清业务目标。浏览器不会再要求用户先勾选文件，也不会提交客户端的 selected_file_refs。它减少了“用户必须先知道答案在哪里”的前置负担。

服务端创建 Run 时冻结完整 allowlisted 输入索引，scope_mode 是 whole_workspace。Planner 只看到安全元数据，它提出本轮需要的资料和分支，服务端再校验预算、来源、依赖、工具和禁止动作。

用户少做了一次文件选择，系统就必须多承担三项解释责任：说明为什么选择这些资料；区分规划模型和分析模型是否调用、是否采用；持续显示当前轮次、剩余预算、阶段和有序 Trace。

这不意味着已经穷举了 96 份资料。即使默认 12 轮、公开上限 24 轮，自主选择仍可能不完整，因此结果继续需要证据核对、成果检查和人工复核。

转场：如果来源文字不能唯一定位，系统不会把整项任务推倒重来。

## P19 实操 2：证据有歧义，只恢复受影响的分支

建议时长：2 分钟

这页展示证据出现歧义时的真实处理。典型情况不是没有源文件，而是模型提供的逐字片段在安全预览里出现多次，服务端无法唯一决定应该回开哪一处。

界面先回答发生了什么、影响什么、用户现在要做什么；然后给出候选位置和安全预览高亮。用户选择的是来源位置，不是在替 Agent 判断结论一定正确。

右下角的小图说明同一轮的不同 Branch 可以有不同动作。DecisionRequest 绑定 expected_version、source_revision、候选和受影响 Branch；来源版本变化时进入 stale，旧选择不能直接应用到新文件。

确认后只恢复目标 Branch，已完成 ArtifactVersion、其他 Branch 和核对记录不被覆盖。这就是局部恢复相对整轮重跑的交互价值。

转场：最后看成果已经生成后，系统如何区分文件事实、业务效果和模型说明。

## P20 实操 3：成果可检查，模型说明不覆盖事实

建议时长：2 分钟

左侧展示成果与业务效果分层。固定场景能够在隔离 Run 工作区生成真实文件，用户可以下载；系统还会执行具名确定性检查，记录 EffectReceipt。付款、核销、发送、写 CRM 等没有发生的动作，继续明确显示为未发生。

右侧展示模型说明与确定性成果冲突时的处理。模型确实被调用，所以 called=true；但它给出的行数或分组与确定性成果不一致时，output_used=false。前台只保留一套当前结论，冲突说明进入审计轨迹。

这一步把“模型说了什么”和“系统采用了什么”分开，也把“文件存在”和“业务动作发生”分开。对用户的直接影响是：成果可以先用，依据可以继续审，错误说明不会覆盖事实。

当前边界是固定检查只证明特定字段、结构和效果，不是通用语义真值证明器。

转场：有了这条当前纵切，下面把它重新放回 07-16 的三个 Demo，分别看时间、组织和动作三个维度哪些已经落地、哪些仍是目标。

## P21 Demo 1：时间维连续性，单个任务如何持续推进

建议时长：2.5 分钟

Demo 1 来自 07-16 的时间维连续性。目标不是让 Agent 永远运行，而是让同一个 Task ID 在多轮任务中拥有稳定的任务契约、状态版本、分支和恢复点。流程仍然是 Task Contract、Observe、Plan、Act、Verify、Commit。

07-16 的关键镜头是 Verify 同时发现正式口径 2,400 万和预测口径 2,680 万。正确处理不是整项任务失败，也不是让模型自行选择，而是 Evidence Gate 只让 revenue-baseline 分支进入 waiting_input。customer-facts 和 project-risk 分支继续产出并保留。

用户随后给出 Steer：采用正式口径，同时保留预测差异说明。系统只恢复受影响分支，最后把版本、来源、验证结果和 Trace 一起 Commit。这样冲突不会扩散，已经完成的工作也不会被新一轮覆盖。

当前系统已经具备服务端 Branch、分支级 Evidence Gate、append-only ArtifactVersion、TaskCommit、局部恢复和可选 PostgreSQL 重启恢复。还没有生产级跨端身份、任意办公工件写入和长期后台 Worker。因此这一页不是把 07-16 演示冒充当前实测，而是说明我们已经完成了其中最关键的一段状态与证据纵切。

前台变化是用户不必重开对话、重讲背景；他在同一任务里看见哪个分支完成、哪个分支为何停、选择后恢复什么、旧成果是否保留。

转场：时间连续性解决以后，Demo 2 处理的是同时有很多待办和复杂分工时，工作如何被组织。

## P22 Demo 2：组织维复杂性，任务怎样拆解并收敛

建议时长：2.5 分钟

Demo 2 仍然保留 07-16 的智能工作驾驶舱作为目标产品面。但这次我们先不画“邮件、CRM、项目、报销、日历”的假任务队列，而是把驾驶舱背后最关键的组织能力做成一个可检查纵切。

输入是一条可以直接复现的办公任务：分别核对产品上线、搜索 Agent 运行和用户交互三条工作线的风险与证据，先独立核对，再形成统一简报。用户只说业务目标，不指定五个 Agent，也不自己管理多个会话。

过程由服务端事实决定。Topology Admission 编译出五个 WorkUnit：三个根工作包先执行，两个依赖工作包等待前序结果。第一波返回后，三个 Contribution 分别进入采用门；只有带批准来源和可定位证据的候选才进入 Artifact。两个依赖工作包显示“下一波待确认”，由用户明确启动，而不是后台无声扩张预算。

输出是一张统一工作面。左侧阶段轨回答现在走到哪，中央 DAG 回答谁依赖谁，右侧当前影响只突出一个主要操作，底部结果条说明三份贡献已经采用、Artifact v1 已保留、还有两个工作包待确认。用户管理的是统一成果和下一步，而不是多个 Agent 对话。

这里的交互依据新增了 Progressive Disclosure：先显示进展和当前影响，再按需展开 Worker 回执、来源范围与证据审查。它支持“默认不把所有协议事实堆在一起”的设计方向，但不证明当前文案一定更好。

边界必须讲清：这是单服务进程、顺序批次、每批最多三个只读执行单元的受控演示样例。它没有持久任务队列、租约、远端执行单元或多实例协调，也不是完整的智能工作驾驶舱；自动化和截图同样不能证明这种协作方式更快、更准或更易理解。

转场：无论任务由单 Agent、Workflow 还是 Swarm 完成，只要下一步涉及真实发送、付款或生产变更，都要进入 Demo 3 的动作风险门。

## P23 Demo 3：动作维风险，方案与执行之间必须有 Gate

建议时长：2.5 分钟

Demo 3 保留 07-16 的 Risk Gate。Risk Lens 从动作影响、数据敏感度、可逆性、权限和缺失信息评估风险，再映射到 L0-L5：L0 自动执行，L1 执行并通知，L2 只生成草稿，L3 普通确认，L4 强确认，L5 直接拒绝。

真正关键的是动作链。Agent 先提出方案，前台展示动作对象、影响范围和可逆性；Evidence Gate 与 Risk Lens 给出来源和风险理由；需要人工确认时，用户明确同意后才生成 Permit；执行后必须返回可核验的 ExecutionReceipt，或者明确写出动作未发生。

页面下半部分使用当前真实界面截图，说明目前已经实现的有限一段：实际 Artifact、具名 Validator、EffectReceipt 和未发生边界可以分层展示。但生产 Connector、身份授权、Permit 防重放与真实外部动作仍未实现，所以系统不会发送邮件、付款、写 CRM 或执行生产命令。

前台的直接变化是按钮不能只写“确认”。用户必须先看见对象、影响、证据、风险级别、可逆性和执行回执，才能知道自己的点击究竟会改变什么。

转场：三个 Demo 的方向保留，但下一步必须继续用可证伪证据而不是更多概念升级结论。

## P24 下一阶段：把 07-16 方向变成可证伪证据

建议时长：2 分钟

最后回到 07-16 的目标：让工作在约束下持续收敛。但这次不只给一张三年路线图，而是把下一阶段拆成五道证据门。

第一，补格式原生 Locator，让 PDF、XLSX 和 DOCX 的引用定位不再主要依赖逐字 quote。

第二，让 Artifact、EffectReceipt、provenance 和未执行边界能够一起导出，让成果文件离开界面后仍然保留审计语义。

第三，把固定成果适配器逐步扩展为可配置业务 Verifier，并用固定数据和失败样本验证，而不是直接声称通用。

第四，把当前进程内 Worker 纵切升级为 durable queue/lease、远端 Worker 与多实例恢复，再接 Tool、Connector、Permit 和幂等回执。只有拿到真实执行回执，才能说外部动作发生了。

第五，冻结同一任务、模型、数据和评价标准做竞品同场挑战，并开展正式目标用户研究。只有这些门通过，我们今天讲的“差异候选”才可以升级成“已验证优势”。

所以最后请大家评审的，不是一句“这个 Agent 看起来更智能”，而是是否同意沿着这五道门继续生产证据。

## 收束

整套方案可以用一句话收束：Office Agent 的目标不是再给用户一段更长的回答，而是让用户始终看见当前结论、来源、成果、人工决定和外部动作边界。

当前我们已经有固定 Workspace、受限 Control Loop、分支级证据门、成果版本、Snapshot/SSE、最小 Task/WorkUnit/Contribution 台账、每波最多三个进程内只读 Worker，以及部分确定性成果验证。尚未完成的是 durable queue/lease、远端或分布式 Worker、通用 Tool Gateway、生产级 Connector、全面语义验证和正式用户价值证明。

因此今天最稳妥的结论是：我们已经验证了一条从办公资料到可复核成果的受限纵切，也明确了它与主流方案在交互重心上的差异候选；下一步要用格式定位、业务验证、真实动作回执、竞品同场挑战和目标用户研究，把候选继续变成证据。

## 常见追问口径

### 1. 你们能做而竞品不能做的是什么？

当前不能严谨地说竞品“不能做”。可以说，我们已经在固定公开办公场景中把 Workspace 范围、Branch 证据门、真实 Artifact、模型说明采用回执、人工决定和未执行边界放进同一审查链。它是值得继续同场验证的差异候选，不是已经证明的独占优势。

### 2. 默认 12 轮是不是太少？

12 轮是当前默认值，公开上限是 24 轮，两者都不是任务质量结论。系统还同时受文件数、模型调用次数和主动运行时间预算约束；是否足够要由完成条件和固定场景实测共同判断。

### 3. 为什么成果正确还会缺引用？

成果检查和证据定位是两套事实。成果文件可以通过结构和确定性检查，但逐字 quote 可能在原文中出现多次，无法唯一回开。缺的是唯一定位，不等于缺源文件，也不等于成果计算错误。

### 4. `completed` 是否代表任务正确？

不代表。当前 `completed` 只说明既定 Schema、引用成员关系、只读边界、分支记录等检查通过，并且结果仍需要人工复核。它不证明自然语言结论全面正确，也不证明业务价值。

### 5. 为什么还要调用模型，固定适配器不是已经能算吗？

固定适配器适合可结构化、可复算的结果，模型仍用于规划、跨资料解释、归纳和提出候选。但模型说明必须服从服务端可验证成果，不能反过来覆盖确定性事实。

### 6. 怎样证明新界面更清晰？

截图和现场反馈只能发现问题，不能证明体验改善。需要目标用户在无引导情况下完成任务，并测量是否能说清当前结果、来源、影响和下一步，同时记录耗时、误操作、恢复成功率和主观负担。

### 7. 当前 Demo 2 是否已经是完整的自适应协作？

只能说已经完成受控纵切：路线准入、工作包依赖图、显式批次、每批最多三个进程内只读执行单元、贡献采用和统一成果。它没有持久任务队列与租约、远端执行单元、多实例调度，也没有同任务同预算的质量或效率增益证据，因此不能直接叫作分布式自适应协作。
