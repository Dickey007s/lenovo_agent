## 可直接观察的事实

- 第一张图显示第 2 轮在 `240 秒` 后进入“到达预算边界”，但仍有 6 条分支未完成、
  0 份文件核对。页面只把整体结果重复为“到达预算边界”，没有区分轮次、模型调用和
  时间三种边界。
- 运行轨迹显示第 1 轮曾进入人工确认，再恢复第 2 轮。此前 Runtime 的 deadline 从 Run
  建立起按墙钟累计，人工阅读与等待也消耗 Agent 时间预算，因此恢复后可能在下一次模型
  调用前立刻停止。
- 第二张图只显示“分支仍缺少证据”和一份候选文件。页面没有 Evidence Anchor，也没有说明
  是源文件缺字段、Agent 没形成结构、还是逐字引用未能唯一定位。
- 用户能查看整份 `上线配置清单.xlsx`，却不知道需要修改哪个文件或字段。事实上这类缺口
  可能来自 Agent 交付未通过校验，并不构成“源文件需要修改”的服务端事实。

## 支持的判断

- 默认 Agent 执行时间预算应从 `120 秒` 提高到 `1200 秒`，允许上限从 `300 秒` 提高到
  `3000 秒`。每轮 1 到 8 份文件的上下文边界继续保留，不能因扩大时间预算而放开来源范围。
- 时间预算只统计 Agent 真正处于 active 状态的时间。`waiting_input`、用户主动暂停和恢复前
  的人工阅读时间不计入；恢复后从已经消耗的 active elapsed 继续计算，而不是重新清零。
- 前台必须显示精确停止原因，例如“模型调用预算已耗尽”或“Agent 执行时间预算已耗尽”，
  不能统一显示抽象的 `budget_exhausted`。
- 没有 Anchor 的 Gap 应被呈现为“Agent 执行缺口”，并明确问题类型、受影响 Branch、尝试过
  的文件、模型是否调用/结果是否采用、已保留内容和未发生动作。
- 用户不应被要求替 Agent 猜行号或修改源文件。补充线索应是可选项；主要动作应是“只重试
  本分支”。如果旧 Run 已终止，则用该分支目标创建新的独立只读 Run。

## 局限

- 这是单一 Stakeholder 的形成性反馈，不是代表性用户研究。
- 截图和本地轨迹能证明旧状态产生了困惑与过早停止，不能证明扩大预算会提高模型质量，
  也不能证明新处置单一定降低理解时间。
- `1200/3000 秒` 是当前演示和真实模型时延下的工程默认值，不是生产 SLA 或成本承诺。
- 新 Run、分支重试和候选文件均不证明源文件有错、结论正确、文件已修改或外部动作发生。
