## 原始反馈

用户在 Task Director 的“读取资料”阶段标记上反馈：

> 我觉得你这里很突兀啊，怎么每次打开都是直接到核对事实这一步了，前面的那些呢，1 2 3步的过程呢，这一下子第四步信息量也太大了，用户难以一下子接受完的。你别怕调用token，该用api就用api调用大模型

## 支持的判断

- 当前单次 `start` 把 Observe、Plan、Act、Verify 一次性提交，导致用户第一次可见的服务端状态已经是第 4 步。
- 阶段轨虽然显示 1、2、3 已完成，但用户没有看见这些阶段各自做了什么，不能把阶段轨当作渐进过程证据。
- Verify 首屏同时展开三条分支、多个工件与一个冲突，信息披露过快。
- 后续应让 1→2→3→4 成为服务端可恢复、可回看的阶段事实；在 Plan/Act 适合的内容生成位置可以调用当前配置模型，但不能让模型决定来源、状态、验证、冲突或提交。

## 局限

这是单一 Stakeholder 对当前固定 Demo 的试用反馈，不是目标用户研究，不证明某个等待时长、动画节奏或模型生成方案一定有效。渐进式交互仍需浏览器回归、运行证据和至少 5 名目标用户的无引导任务测试。
