# 用户反馈：Demo 1 与 Demo 2 分开展示，并显式呈现 Adaptive Swarm

- 日期：2026-09-01
- 类型：Stakeholder 产品反馈与研发授权
- 状态：`Recorded`
- 关联决策：`DR-0056`

## 原始诉求

1. Demo 1 与 Demo 2 的演示需要分开；每次聊天应隔离为一个独立会话，用户可以回看之前
   的运行记录。
2. Demo 1 继续突出 Agent Control Loop 的时间维特征，即“同一个任务跨轮次、跨 Run
   如何继续”。
3. Demo 2 突出复杂任务如何拆解、是否协作以及怎样收敛；使用单独的弹出工作台展示完整
   要素，避免受主页面空间限制。弹窗外保持 Demo 1 的原有设计。
4. Demo 2 必须明确体现 07-16 方案中的 `Adaptive Swarm`，不能让用户只能看到零散的
   Worker、WorkUnit 或内部台账而看不出产品主线。

## 支持的产品判断

- 用户首先管理的是“任务会话”，不是无边界增长的一条页面；不同 `task_id` 应成为不同
  会话，同一 `task_id` 的多次 Run 应在会话内形成可回看的时间线。
- Demo 1 与 Demo 2 共享同一个 Runtime 和事实对象，但需要两个不同的信息架构焦点：
  Demo 1 解释时间维连续性，Demo 2 解释组织维协作。
- Demo 2 需要一个独立、宽阔且可核验的协作工作台；主页面不应同时承载完整 Loop、
  Worker 台账和共享成果收敛的全部细节。
- `Adaptive Swarm` 可以成为面向用户的路线名称，但必须同时说明当前实现只是受限、
  进程内、只读 Worker 纵切，不能把目标架构当成当前能力。

## 不支持的推断

- 这是单一 Stakeholder 的形成性反馈，不是目标用户研究，也不证明新界面更易理解、
  更高效或更可信。
- 反馈不授权新增伪造的 Demo 数据、Scenario API 或浏览器本地历史权威。
- “需要体现 Adaptive Swarm”不等于当前已经具备动态扩缩、分布式队列、Worker lease、
  Connector、真实 Tool Gateway、冲突解析器或外部动作能力。

## 后续验证

实现后至少需要自动化验证任务会话隔离、同 Task 的 Run 谱系、历史 Run 只读、
Adaptive/非 Adaptive 两条工作台路径、1440 px 与 390 px 布局、键盘关闭与公共字段脱敏。
这些工程门仍不能替代目标用户的可理解性测试。
