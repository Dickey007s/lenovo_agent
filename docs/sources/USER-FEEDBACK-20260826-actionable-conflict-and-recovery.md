## 支持的判断

- “打开原文”只是可核对的起点。问题页还必须把冲突拆成编号事实，并说明是否真的需要人
  决定、为什么不能由 Agent 继续推断、用户有哪些互斥选项。
- 人的选择必须形成服务端拥有的结构化决定和回执，并明确它将影响哪个 Branch、下一轮会
  读取什么、会重新执行什么、不会发生什么外部动作；不能只把一句自然语言塞回聊天框。
- 证据位置不能唯一匹配通常是“需要消歧或降级”的可恢复问题，不应无条件等同于整个 Run
  的 terminal `failed`。未受影响的 Branch、已核对结果和 ArtifactVersion 应继续保留。
- 失败界面必须给出原因类别、已保留内容、下一步动作和恢复位置。只有安全完整性、任务合同
  损坏或无法建立可信状态等错误，才应直接关闭整条路径。
- 长解释可能提高说服力，却不必然提高正确的人机协作。高影响决定应优先展示可比较证据与
  决策后果，必要时先让用户形成初始判断，再展示 Agent 建议。

## 局限

- 这是单一 Stakeholder 的形成性反馈和两张真实界面负例，不是代表性用户研究。
- 截图证明当前交互产生理解与恢复缺口，不证明本文提出的 Decision Packet、候选消歧或
  分支恢复一定能降低时间、提高正确率、信任或业务价值。
- 截图不证明 Agent 的 Finding 正确，也不证明两个文件中的记录应由哪一方作为业务真值。
- 后续实现仍须分别留下源码、协议、自动化、真实运行和用户研究证据；不能把本记录当作
  `Limited Verified` 的实现 Evidence。
