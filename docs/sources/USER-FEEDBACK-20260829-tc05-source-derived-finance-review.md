# USER-FEEDBACK-20260829-TC05-SOURCE-DERIVED-FINANCE-REVIEW

## 来源

- 类型：Stakeholder 场景验收、历史实现审计与工程验收边界
- 日期：2026-08-29，Asia/Shanghai
- 场景：FORTE 固定 `Finance-018`，三份往来明细 XLSX 的期末明细与跨期风险候选
- 状态：已记录；实现结论由 `DR-0046` 与对应 Evidence 单独验证

## 问题定位

历史 `_finance_reconciliation` 先生成未付、未收和所谓僵尸账款列表，再用同一列表检查自己；`check-finance-zombie` 把“候选必须为 0”当成成功答案。它无法证明成果由本轮冻结的三份 XLSX 重新推导，也会在来源合法变化真的产生候选时制造 false red。两个 CSV 与三期说明的来源和业务含义也没有形成一套可持久化、可展开的公共事实。

Stakeholder 要求把 TC-05 改为来源推导的固定纵切：

1. 严格绑定 `Finance-018` 三个期间工作簿，解析业务行和 Excel locator；重复键、未知方向、公式、错误值、非法金额或来源错配必须 fail closed。
2. 两个 CSV 只描述 2026 期末未付/未收；Markdown 才进行三期比较。每张成果卡在下载前说明期间、口径和用途。
3. “僵尸账款”只能称为候选启发式。候选 0、1 或多条都可以通过来源复算，不能要求空集合。
4. Verifier 必须重新解析批准来源与生成字节，不能由生成前列表自证。
5. 前台分开确定性文件检查、当前明细/候选和最终财务处置；候选大于 0 用琥珀色人工复核，不作为系统失败。
6. 输出与回执必须明确没有付款、核销、记账、坏账确认或原文件修改。
7. 来源变异、输出篡改和 PostgreSQL 重启都要有可复现门，浏览器 fixture 必须来自服务端公开 manifest。

## 完成条件

- 当前批准来源动态得到 31 条未付、2 条未收、0 条候选及对应合计；这些是固定版本观测，不进入生产判定常量。
- 测试副本将 2026 绵阳长城余额改为 150 万后形成 1 条候选，三份成果和 EffectReceipt 仍通过；再改变任一期间可以解除候选。
- 两个 2026 CSV 在只修改旧期间且未形成候选时字节不变；跨期说明按来源变化。
- 三份成果可下载并独立解析；PostgreSQL 重启后 Snapshot、EffectReceipt、Artifacts 和 `finance_review_outcome` 保持一致。
- 1440 px 和 390 px 前台可清楚查看三种状态、候选三期金额和 locator，不以绿色 Artifact 暗示会计处置已发生。

## 局限

这是单一 Stakeholder 的形成性验收，不是财务用户研究、会计政策审核或生产账务系统测试。固定 `Finance-018` 启发式不能外推为通用总账、应收应付、账龄、坏账确认、多主体、多币种、Connector、多 Worker 或外部动作能力。
