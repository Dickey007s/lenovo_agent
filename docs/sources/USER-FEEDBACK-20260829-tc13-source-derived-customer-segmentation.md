# USER-FEEDBACK-20260829-TC13-SOURCE-DERIVED-CUSTOMER-SEGMENTATION

## 来源

- 类型：Stakeholder 场景审计、交互验收与工程验收边界
- 日期：2026-08-29，Asia/Shanghai
- 场景：FORTE 固定 `sales-020`，依据公开问卷 CSV 与分类/报告规则 Markdown 生成画像清洗台账和销售策略草案
- 状态：已记录；实现结论由 `DR-0049` 与对应 Evidence 单独验证

## 问题定位

历史 `_customer_segmentation` 把固定样本 ID、固定 `8` 条分类、固定排除名单、阈值、优先级和销售话术写入生产实现，再用同一批内存结果检查自己。它只能证明固定答案仍在，不能证明来源合法变化会进入清洗、分类、报告和前台。旧输出还把没有来源支持的产品功能、话术和销售优先级写成确定性建议，容易让用户误以为系统已经完成真实客户研究或销售验证。

Stakeholder 要求把 TC-13 改为来源推导的固定纵切：

1. 严格绑定一份批准问卷与一份批准规则，CSV/Markdown 中未知、重复、冲突、非法或多出的规范不得静默忽略。
2. 每个原始样本保留来源行、原始值、清洗值、转换、全部命中画像、优先级裁决、最终标签或排除原因；生产成功条件不得保存当前样本 ID 集合。
3. “重复样本”的来源没有定义键。当前固定适配器只能采用公开、保守的 `exact_non_id_payload` 假设，并明确要求销售负责人复核。
4. canonical 中没有样本同时命中多个画像，因此不能把优先级显示成已经被当前来源验证；必须另设真实多标签变体证明动态裁决。
5. 规则只批准报告栏目，没有批准话术、产品功能或跟进顺序。前台只能显示待补充/批准模板，不能把策略草案写成确定性业务结论。
6. Verifier 必须重新解析批准源字节和两份最终工件；阈值、优先级、新样本、缺失默认或样本 ID 的合法变化应动态生效，成果篡改和非法来源必须转红。
7. 前台分开来源与工件验证、画像清洗事实、重复口径与策略人工复核、真实客户/CRM/商机/营销动作未发生。

## 完成条件

- 当前批准来源动态得到原始行、唯一载荷、重复、分类、无法归类、画像分布与 priority witness；这些只作为当前版本观测，不进入生产判定常量。
- 阈值、优先级、缺失默认、合法新样本和多标签 witness 变异会改变相应样本与汇总，不产生旧固定 ID false red。
- Markdown 与 CSV 可下载并独立解析；PostgreSQL 重启后 Snapshot、Artifact、EffectReceipt 与 `customer_segmentation_outcome` 保持一致。
- 1440 px 和 390 px 前台显示四层事实、逐样本来源与规则 locator，且无横向溢出。

## 局限

这是单一 Stakeholder 的形成性验收，不是销售负责人批准、真实客户研究、销售效果验证或用户研究。固定 `sales-020` 适配器不联系客户、不写 CRM、不创建商机、不触发营销，也不构成通用分群引擎、Connector、多 Worker 或生产决策系统。
