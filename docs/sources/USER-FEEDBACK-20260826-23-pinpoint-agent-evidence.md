# USER-FEEDBACK-20260826-23：把 Agent 判断精确标到原文位置

## 原始触发

Stakeholder 在当前工作台打开 Finding 审查页后反馈：

> 可我还是没办法直接很方便的直接看出来 agent 指的是哪里有问题，需要更好的前端设计来标记出来，想办法让用户更清晰。

随反馈提供的截图显示：页面已经把 Finding、关联的 `workflow.py` 与
`search_agent.log` 放到同一审查页，但仍只展示长段判断和整份文件预览。用户必须自行在
代码和日志中搜索，才能猜出“设计预期”和“实际观测”分别来自哪里。

负例截图：[`dr-0029-before-unlocated-evidence.png`](../evidence/screenshots/dr-0029-before-unlocated-evidence.png)。

## 支持的判断

- Finding 不能只绑定文件，必须把可复核依据拆成原子证据并精确定位到安全预览中的
  文本行或表格行。
- 对“设计与运行不一致”一类问题，前台应把“设计预期”和“实际观测”并列呈现；点击任一
  证据后，文件预览应切换到对应文件、滚动到对应位置并高亮。
- 精确位置不能由浏览器根据 Finding 文案猜测。模型只能提交逐字引用候选，服务端必须在
  本轮已批准的安全预览中唯一匹配后生成位置事实。
- 服务端无法唯一定位时，前台必须明确显示“只能定位到文件”，不能伪造行号或高亮。

## 局限

- 这是单一 Stakeholder 的形成性反馈与一张负例截图，不是多用户可用性研究。
- 反馈证明旧交互的定位成本高，不证明新设计一定降低核对时间、提高信任或提升任务正确率。
- 安全预览中的 PDF/DOCX 行号是提取文本行，不是原生页面坐标或 Word 段落编号；表格当前
  定位到行，不声称定位到精确单元格。
- 原文位置与引用成员关系仍不等于语义蕴含、数值正确、穷举完成或 Finding 结论成立。
