## 用户要求

用户要求以原始指令“把搜索 Agent 从固定 Workflow 重构为带迭代上限和轨迹的 ReAct 结构。”真实运行 `deepseek-v4-pro`。Agent 必须从服务端批准的 algorithm-013 输入复制完整 `search_agent_workflow` 到隔离 Run Workspace，在真实副本上改造主入口并保留原业务契约；下载 ZIP 后还要独立解压、编译和执行测试。

前台不能只显示“代码包”和绿色检查数。普通用户应直接看懂：改的是隔离副本；固定五节点变成了什么；迭代上限为何存在；轨迹只记录可审查动作/观察；哪些文件修改或保留；如何下载、自测和人工合并；当前没有写回仓库、联网生产搜索或形成通用代码沙箱。

第二轮独立审计进一步要求拆开两层事实：生成副本中的 `DefaultReActPolicy` 只是确定性地依次选择已规划工具，虽有可替换的 `action_policy` 接口，但没有证明模型会根据 Observation 自主决定下一动作；外层真实 `deepseek-v4-pro` Planner/Analyst 调用也不能冒充工件内部策略。面向用户的名称和说明因此应使用“有界 ReAct 控制结构/可插拔策略”，而不是“已实现模型自主 ReAct”。

合并前的计数审计又发现：两份成果都挂载了同一组 12 个 `check_id`，旧顶层却显示 `24/24`，EffectReceipt 也写成执行 24 项。这会把同一清单的两个展示位置误报成 24 个独立检查。用户要求服务端回执、SSE 和前台汇总都按 `check_id` 去重，写成“2 份成果共享 12 项确定性检查，12/12 通过”；单张成果卡可以保留 12/12，并明确“使用同一验证清单”。

## 支持的判断

- TC-02 必须以完整源码副本、真实 diff、测试清单和下载后独立复测作为效果门。
- 模型调用、模型输出采用、确定性代码效果和整个 Run 状态必须分开显示。
- 失败包可以保留用于排查，但必须红灯并明确不要合并及如何重新运行。
- 模型调用回执、工件内部控制策略、可见 action/observation 轨迹必须分层展示，避免把外层 Provider 事实错误归到下载代码包。
- 当前测试数量来自本版测试清单，不是业务上限；Verifier 应比较声明与实际执行的测试 ID。
- 多个 Artifact 复用同一验证清单时，Run 汇总必须按 `check_id` 去重；卡片级投影数量不能冒充独立检查数量。

## 不能支持的判断

- 单一 Stakeholder 反馈不是目标用户研究，不证明新前台提高理解、效率或信任。
- 固定 algorithm-013 适配器不证明任意仓库代码改造、生产安全沙箱、网络隔离或自动 PR 能力。
- 本次固定测试未调用网络或生产搜索，且未注入凭据和代理；runner 没有 OS 级 socket 隔离，不能写成通用“网络已禁用”。
