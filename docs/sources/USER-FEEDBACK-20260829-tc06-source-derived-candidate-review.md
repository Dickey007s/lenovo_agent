## 问题定位

历史 `_candidate_review` 把岗位与候选人的结论直接写成固定答案，再检查生成文档是否含有同一批答案。它没有证明答案由本轮冻结的 JD 和简历逐条推导，也不能在来源发生合法变化时只改变受影响候选人。因此历史绿色结果不能支持“岗位匹配效果已验证”。

Stakeholder 要求把 TC-06 改为来源推导的固定纵切，而不是继续修饰旧文案：

1. 只允许 `hr-001` 的两份 JD DOCX 和五份简历 PDF；缺失、额外、重复、同内容冒充、空或损坏文件、姓名串线均须 fail closed。
2. 岗位条件与候选事实必须保留服务端安全位置和摘录。同一候选在两个岗位复用同一份来源，但两个岗位的判断独立计算。
3. 条件状态使用 `met / not_met / unverifiable / human_exception_required`。未写到不等于不满足；存在 JD 明示例外时不得自动淘汰。
4. 输出两个岗位报告和一份逐条件台账；Verifier 必须从批准来源重新计算，而不是从报告反向证明报告。
5. 前台同时显示确定性文件检查、岗位匹配建议和最终 HR 决定三种事实，首屏明确“不是录用或淘汰决定”。
6. 默认隐藏邮箱、手机号、地址、性别、年龄、照片及明显人口属性代理字段。当前没有公平性用户研究或人口属性评估，不得声称无偏。
7. 来源变异、阈值变异、字段串线、损坏来源、隐私泄漏和输出篡改都必须能够使系统结果发生可解释变化或明确转红。
