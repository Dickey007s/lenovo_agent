## 用户要求

用户以普通办公语言要求 Agent 依据统一规则核查六份授权委托书，逐项说明风险、资料不足和复核动作。系统只能读取固定 FORTE `Legal-020/input` 的一份规则 Markdown 与六份 DOCX，必须从来源规则、字段和原文位置动态形成结论，不能把历史预期的风险等级或数量写进实现，再用同一组常量自证为绿。

用户独立检查了六个 DOCX 包。六份文件最后均只有空的“委托人签名”或“委托人盖章/法定代表人签名”占位；包内没有 `word/media`、`w:drawing`、`w:pict`、嵌入对象或数字签名。历史实现曾以“样本保留签署栏”为理由排除 R05，这与公开规则字面冲突。当前没有获批的 `draft_unsigned=true` 例外，因此应按来源触发 R05，同时明确这仍不是真伪鉴定。

委托书 4 的受托人写为律师，但没有身份证号或律师执业证号，除 R01、R02 外还应动态触发 M03。委托书 2 和 6 虽出现执业证号，当前系统没有律师资格 Registry 或 Connector 回执，因此只能标为 `unverifiable`；字段存在不能冒充资质已核验。非律师自然人的诉讼代理资格也依赖未提供的关系或法院许可材料，不能猜测。

用户还指出主体字段必须隔离：委托人缺少证件时，不能从受托人行或全文第一个号码补上 R01；企业判断也不能被无关主体的统一社会信用代码污染。每个判断需要绑定文档、规则、原文位置、事实、规则判断、责任人、处置动作和退出条件。

## 前台与交互影响

前台必须并列显示三种不同事实：文件和计算是否通过确定性检查、法务业务 Gate 是否通过、签署与人工复核是否仍待处理。用户应先看到“不得据此签署，必须法务复核”，再按文件展开 21 条规则；绿色文件检查不得暗示授权有效或已经签署。

这条反馈支持建立来源推导的逐项台账、DOCX/CSV 下载物、三状态前台、字段串线负向门和 Registry 缺失边界。它是单一 Stakeholder 反馈，不是正式法律意见、法律效力认定、用户研究或通用合同审查能力证明。
