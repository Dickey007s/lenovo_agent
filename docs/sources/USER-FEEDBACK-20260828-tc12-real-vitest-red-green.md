## 用户要求

用户以普通指令“为三个看板工具模块编写 Vitest，修复源码并真实运行测试。”触发任务。系统必须复制 FORTE qa-003 `dashboard-toolkit` 的完整 11 文件输入到隔离 Run Workspace，并用同一套真实 Vitest 先证明未修复源码确有缺陷，再应用修复并复测。原 FORTE 输入始终只读。

用户拒绝只把历史 `9/9` 改成更大的数字。旧纵切只有修复后绿灯，缺少未修复红灯、逐文件 coverage、统一 diff、机器可读测试清单、下载后独立复跑和准确的网络边界，因此不能证明测试抓住原缺陷，也不能让用户自行检查。

本轮要求保留四个分阶段事实：原配置的别名解析失败；只修配置后暴露增长率分母、排序副作用和日期函数未导出；只补导出后暴露日期闭区间缺陷；完整修复后同一清单全部通过。前台必须显示三个真实 suite、测试文件、数量和可展开测试 ID，并把“改隔离副本、人工审查后合并、没有自动 PR”放在首屏可见位置。

## 影响与边界

这条反馈支持把 TC-12 的效果门从“有 Vitest 绿灯”提升为“真实副本、同测集先红后绿、逐文件 coverage、下载独立复跑和前台清单一致”。它是单一 Stakeholder 反馈，不是用户研究，也不证明任意 JavaScript 项目自动修复、生产多租户隔离、OS 级断网、自动 PR 或模型稳定质量。
