- 类型：Stakeholder 场景审计、交互验收与工程验收边界
- 日期：2026-08-29，Asia/Shanghai
- 场景：FORTE 固定 `Operations-008`，依据 `运营管理/专业性说明.md` 形成 M1 逾期外呼流程设计
- 状态：已记录；实现结论由 `DR-0047` 与对应 Evidence 单独验证

## 问题定位

历史 `_compliant_outbound_flow` 先写死一组节点、边、终态和 13 项检查，再用同一批常量检查自己。它只能证明固定答案仍在，不能证明流程来自本轮冻结的批准 Markdown。旧流程还把录音告知放在身份确认之前，并加入来源不存在的第三方升级路径；当来源合法修改时段、频次、保存年限、重拨间隔或转人工条件时，成果不会随之可靠变化。

Stakeholder 要求把 TC-10 改为来源推导的固定纵切：

1. 严格绑定唯一批准来源，按安全行号解析规范性要求；未知、重复、冲突或非法规则必须停止，不得静默忽略。
2. 生成稳定 ID 的可遍历状态图，每条来源要求必须映射到节点、边、守卫或终态；所有终态必须从唯一 START 可达。
3. 当前来源要求身份确认早于录音告知与欠款披露；第三方路径只能转告或禁呼，不得泄露金额。
4. Verifier 必须重新解析批准 Markdown 和生成后的 DOCX 表格，不能由生成前的图对象自证。
5. 前台分开来源/DOCX/图结构检查、规则覆盖、最终合规审批和真实外部动作；绿色 Artifact 不能暗示已经拨号、写 CRM、发短信、写禁呼名单或转人工。
6. 来源参数与新增可识别转人工规则必须动态改变图和前台；未知规范、无路径终态或成果篡改必须转红。

## 完成条件

- 当前批准来源动态解析出规则组、原子要求、图节点、边、守卫与终态数量；这些是固定版本观测，不进入生产成功常量。
- 时间、频次、录音保存年限、重拨间隔和身份/录音顺序的合法来源变异只改变相应参数或路径。
- 新增“高龄或重病必须转人工”能增加规则、守卫和路径；未知规范与不可达新终态不能绿色通过。
- DOCX 可下载并独立解析；PostgreSQL 重启后 Snapshot、EffectReceipt、Artifact 与 `outbound_flow_outcome` 保持一致。
- 1440 px 和 390 px 前台能看到四种并列事实、逐规则来源位置和无执行边界。
