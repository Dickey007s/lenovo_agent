# USER-FEEDBACK-20260826-20：补齐 Demo 1 的分支与成果控制

## 原始触发

Stakeholder 询问 Demo 1 当前完成度。项目明确列出三个主要缺口：服务端真实任务分支图与
分支级暂停/继续、独立不可变的成果版本与可追溯恢复、以及当前 Harness 的真实
PostgreSQL 跨 Runtime 重启验证。Stakeholder 随后回复：“那你继续，把该补的东西补了”。

## 支持的判断

- 可以继续在统一 `Agent Control Loop` 上补齐上述纵切，而不是制作新的 Demo 专用开关。
- Demo 1 的“分支管理”需要成为服务端事实和用户可操作对象，不能只把模型计划画成流程图。
- 成果恢复需要保留历史，而不是覆盖旧结果；用户需要看见 Agent 操作对当前成果指针的影响。
- 持久化主张需要真实 PostgreSQL 进程和顺序 Runtime 验证，不能只依赖共享内存模拟。

## 局限

- 这是单一 Stakeholder 的实现授权和产品方向，不是目标用户研究。
- “补齐”不授权宣称 Demo 1 已达到生产级，也不证明分支交互更易懂、模型结论更正确或任务效率提高。
- 多 Worker 并发、跨实例 lease、真实 Tool Gateway、源文件写入、Connector 和外部动作仍需独立实现与验证。
