# DR-0080：参考图驱动的信息层级减法

## 场景与来源

用户重新确认四张早期 Image 2 界面概念图，要求比较现有页面、减少冗余。
本次原代码截图发现：根工作台的已完成分支先在交付清单列一次，随后执行区再列；
能力进展页有真实文件时，成果检查摘要与当前成果清单重复；协作页先铺大段统计，再出现依赖图。
nanoMuse 只沿用 10 月 7 日固定版本研究中的信息分层原则，不复制组件或推断竞品最新行为。

## 前台交互影响

- 根工作台只有在所有分支 completed 时省略交付清单内的重复分支行。完整分支仍可从原执行区展开。
- 存在任一未完成分支时保留原交付清单，避免跨轮次的待办随当前执行轮次切换而丢失。
- 能力进展页有真实文件时保留前置成果检查/业务结论和唯一成果入口，后方清单只显示“工作项”。无文件时原逻辑成果摘要不变。
- 协作页保留工作包依赖图、当前影响、批准范围和启动按钮；详细准入、调用、采用统计移入原“查看执行回执”。路线解释仍在原展开区。
- 取消部分外层框线、提升工作项状态与正文大小；窄屏成果摘要改成两列，不缩小字挤入四列。
- 完整执行记录、原文确认页、候选无默认项、所有原控制和恢复入口不更改。

## 后端事实映射

`branches[].status` 决定根清单是否仅显示成果摘要。`workspace_artifacts.length` 决定能力页是否已有前置成果区。
工作包图仍只取既有稳定 ID 与 depends_on；回执计数仍分别读取 model_called、output_used 和 gate_status。
详情开关属于原生 details 的本地状态，不提交命令、不关闭事件流、不调用模型，不修改任何版本、来源或权限。
业务否决、文件失败、未知回执、来源变化、预算与控制仍遵守原合同。本轮不改 Runtime 或 API。

图连线、回执展开零新增 POST、键盘操作及统一入口兼容。详见 Evidence。
没有真实模型新任务、数据库重启、外部动作或目标用户实验。不声称所有冗余已消除、与概念图像素一致或体验收益已证明。
