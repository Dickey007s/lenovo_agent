# Demo3：原系统内的人机共驾边界、规则与办公案例

日期：2026-09-12。状态：**Draft，研究设计候选**。这是对既有论文和项目合同的定向归纳，不是新 Runtime、业务授权器或用户效果验收。

依据：[本次整合要求](../sources/USER-FEEDBACK-20260912-integrate-copilot-in-existing-system.md)、[产品入口](../../README.md)、[汇报治理](../DECISION_AND_REPORTING_GOVERNANCE.md)、[DR-0062](../decisions/DR-0062-dynamic-boundary-design-experiment.md)。正式产品继续使用办公资料库 `/` 和 `/agent-capabilities`，保留同一 Task/Run/Snapshot、Agent Control Loop 与 Adaptive Swarm。下文案例是评审镜头，不是新增 Demo 选择器。

## 1. 三个 Demo 各回答什么

| 视角 | 用户实际问的问题 | 现有底座 | Demo3 不应取代什么 |
| --- | --- | --- | --- |
| Demo1：时间连续性 | 今天没做完，明天如何接着做？旧成果是否保留，哪些材料要重核？ | 有界 Run、稳定 Task、单 Branch child Run、不可变成果历史 | 不能把确认后继续画成旧 Run 无限续命，也不能覆盖历史 |
| Demo2：组织协作 | 工作为什么拆给多个 Agent？谁做完了，谁阻塞了谁，返回的内容是否真的被采用？ | Topology Admission、每波最多 3 个显式确认的进程内只读 Worker、WorkUnit/Contribution 台账 | 不能把 Swarm 换成一排人机审批框，也不能把可视分支当并行执行证据 |
| Demo3：决策权限与责任 | 这一步为什么轮到我？我是在选依据、允许继续计算，还是批准业务动作？选择后谁负责什么？ | 优先复用 Branch、EvidenceResolution、DecisionRequest/Record、版本和现有控制回执 | 不是第三个 Runtime；新增业务授权、外部动作和角色责任合同必须另行设计 |

一句话汇报：**Demo1 管“接着做”，Demo2 管“分开做、合起来”，Demo3 管“这一刻谁能决定什么、出问题后谁来处理”。三个视角共同解释一项办公任务。**

这里的“责任”首先指可观察的操作与核对职责，不等于系统已经判定法律责任、组织审批权或生产身份。当前 `X-User-Id` 只是演示 Owner。

## 2. 边界不压成一个等级

同一份报告可以“允许生成内部副本、需要澄清一条规则、禁止实际外发”。因此不以 L0-L5、风险总分或用户熟练度决定所有动作。

| 边界维度 | 要核对的事实 | 对当前任务的影响 |
| --- | --- | --- |
| 可逆性与外部影响 | 只读、隔离成果、源文件修改，还是发送/付款/上线？外部后果能否撤回？ | 当前只读与有限隔离产物可按既有合同执行；发送、付款、生产变更不在能力内 |
| 证据确定性 | 是唯一位置、多候选、无法定位、规则冲突，还是全文尚未读完？ | 不同缺口需要不同处理者，不能统一要求用户“确认没问题” |
| 授权与职责 | 哪个主体可对哪个对象做什么？只是提供内容信息，还是允许调用或业务执行？ | 现有来源选择和 Worker 确认不能充当外发、签署或组织审批 |
| 版本与时效 | 来源是否变更，决定是否仍绑定当前 Run/Request/候选？ | 旧候选不得被静默复用；终态继续要创建同 Task 的新 Run。通用授权期限仍未实现 |
| 结果可观察性 | 有调用、返回、采用、已验证文件，还是只收到超时？ | 成果验证、业务结论、执行和回执分开；未知响应不能显示为成功或未发生 |

### 可组合的应对方式，不是升级阶梯

- **继续并留痕**：已批准范围内的只读、规则明确的确定性处理；不是每一步都让人点同意。
- **保留成果、提示限制**：已有可用产物，但某条说明待补位置或业务判断未通过；不能把整项任务涂绿。
- **只问一个必要问题**：存在真实候选或缺少决定所需的口径；问题包含具体对象和选择后果，不要求用户猜内部错误。
- **暂停受影响部分并提供恢复**：当前合同下由服务端控制安全点和恢复范围；保留其他成果，不承诺任何类型的暂停都立即生效。
- **拒绝或交由有权人员处理**：当前不支持、权限不足、完整性失败；用户点击确认不能覆盖硬限制。
- **明确批准一次具体动作**：仅作为将来的外部执行设计。需绑定对象、内容版本、范围、有效性和独立执行回执；当前不能提供假执行按钮。
- **先核对状态，不重复提交**：当前控制请求未知时按幂等键和 Snapshot 对账；未来外部动作还需 Connector 独立对账，现系统尚无该能力。

顺序原则：先判断能力/授权与完整性，再看证据和版本，最后才优化打扰次数与处理成本。省几次点击不能抵消没有权限、未读材料或未知执行结果。

### 必须拆开的三种“确认”

| 用户实际动作 | 当前语义 | 不代表 |
| --- | --- | --- |
| 选择一处原文依据 | 当前 DecisionRequest 下的候选选择和服务端决定记录 | 结论已经正确、规则获批、文件已修改、外发获准 |
| 启动受限 Worker 或继续一条分支 | 在批准来源、预算、版本和现有只读边界内开始一次处理 | 递归增兵、任意读写、以后永久免确认 |
| 批准业务执行 | 当前没有通用审批和外部执行合同 | 不能用前两项替代，也不能用“我已确认”文本制造该能力 |

## 3. 八个可汇报、可反驳的办公案例

以下“已有”表示当前合同及定向源码所支持的范围，不表示本轮重新执行了全部测试。“待实现”不是获准接入的 API。所有案例当前均保持 `external_action=none`。

### C01 财务成果已生成，Agent 自己没有补齐表格位置

- **任务与触发事实**：分析 Finance-018 往来款资料；确定性产物检查通过，但一条摘要缺少 `2026往来明细.xlsx` 的原表格行/单元格位置。材料存在，不是用户漏传。
- **Agent 可继续 / 必须停止**：保留已生成文件与已采用部分；不能说金额错误、文件生成失败或要求用户修改原表。当前待恢复分支按既有控制合同暂停，不宣称后台仍自动重试。
- **用户动作与前台落点**：原任务进展先展示可查看的成果，再给“查找原表格位置”这一主动作。说明“无需修改文件，只重新处理这一项”；可选线索和审计细节折叠。
- **恢复与依赖影响**：非终态按当前版本恢复目标 Branch；终态走同 Task child Run。只按批准来源重新核对，其他成果与旧版本保留；重试仍可能失败，不能预告一定补齐。
- **已有 / 待实现**：已有成果优先、`source_location` 恢复和版本控制；无“所有来源定位错误必能自愈”的保证。[DR-0038](../decisions/DR-0038-user-language-source-location-recovery.md)、[DR-0034](../decisions/DR-0034-one-action-recovery-and-explicit-source-choice.md)、[当前 API](../API.md)
- **测试反例**：没有任何已验证文件时，页面不得说“成果已生成”；有文件但重试失败时文件仍在；用户拒绝填写说明也能按合同重试。

### C02 同一句话出现多次，选择后原文件又变了

- **任务与触发事实**：核对搜索 Agent 运行日志或 PRD 中一条判断；服务端定位到多个真实候选。用户打开期间来源 revision 变化，或旧 Run 已不是当前任务状态。
- **Agent 可继续 / 必须停止**：保留其他结论及旧成果；不能默认选择第一处、猜行号、把旧候选当新来源，或因用户曾看过页面就视为同意。
- **用户动作与前台落点**：在既有专注核对页显示“哪条判断、N 处原文、选择影响”。未选时不可提交；过期时说明需刷新核对，不显示可复用的旧批准。
- **恢复与依赖影响**：服务端重新校验 Request、候选和来源 revision 后记录决定。终态记录依据不自动继续执行，另由显式 `/continue` 创建同 Task child Run，按当前来源重核所选 Branch；旧 Run 不变。
- **已有 / 待实现**：已有 EvidenceResolution、DecisionRequest/Record、来源过期拒绝和双版本 continuation；通用“任何内容编辑均使业务授权失效”的机制未实现。[DR-0032](../decisions/DR-0032-persistent-decision-and-local-recovery.md)、[DR-0053](../decisions/DR-0053-durable-task-lineage-and-explainable-topology-admission.md)、[当前 API](../API.md)
- **测试反例**：确认响应丢失不能显示“没有记录”，应复用原幂等键/刷新权威状态；过期选择零状态变更；位置确认不能使 `external_action` 变成发送。

### C03 日志可在页面展开，不代表 Agent 已读完整

- **任务与触发事实**：汇总搜索 Agent 日志的分类与路由行为。历史真实验收 Q-01 中，后段有 news 路由反例，但单文件模型输入只保留前 12,000 字符；摘要却未限定只读前段。
- **Agent 可继续 / 必须停止**：可保留范围明确且有依据的局部观察；设计上必须阻止“已全面核对整份日志”的假完整结论。不能以引用可定位或 `output_used=true` 代替覆盖证明。
- **用户动作与前台落点**：未来在原任务成果旁说明实际覆盖与未读范围；不让用户用“确认完整”替系统证明未读内容，也不要求用户猜缺失行号。当前只能人工审查覆盖限制，不能提供尚未实现的续读按钮。
- **恢复与依赖影响**：未来需有可审计的分段读取、未读区间和完成门，受该摘要影响的下游先不采用整库结论。现有重复同范围运行不会自动解决截断。
- **已有 / 待实现**：当前源码有输入截断及 `truncated` 标记；**覆盖与续读合同仍未实现，Q-01 未修复**。这不同于部分固定适配器读取完整批准文件。[失败 Evidence](../evidence/DEMO12-SELF-TEST-ACCEPTANCE-EVIDENCE-20260911.md)、[输入源码](../../services/api/app/application/benchmark_workspace_catalog.py)
- **测试反例**：在读取上限之后放置可推翻摘要的事实；即使前段引用都能准确定位，完整性验收仍须失败。另设无后段反例，避免把任何长文件都误判为内容错误。

### C04 交互问题频率恰好 3%，来源规则的边界写法冲突

- **任务与触发事实**：对 uiux-021 全工作簿的交互问题排优先级；规则文档对 3% 的包含关系存在冲突，恰好落在边界的组无法唯一确定频率档位。
- **Agent 可继续 / 必须停止**：按完整批准工作簿计算明确部分、保留两种规则证据；不替组织挑选更方便的口径，不为冲突组套用优先级矩阵。具体方案仍是待评审建议。
- **用户动作与前台落点**：在现有 UX 成果审查中单列“哪些组受影响、两种规则分别会怎样”。由业务规则负责人决定口径，而不是让任意浏览者选一个原文位置就宣布业务规则获批。
- **恢复与依赖影响**：待实现的规则决定应有明确来源、责任主体和版本，再重算受影响组；旧 CSV 保留，不静默改写。用户仅提出意见时，其他明确计算可供审查，但冲突不自动消失。
- **已有 / 待实现**：已有完整 XLSX 分析、`rule_conflicts`、`human_review_required` 与无批准方案来源的标记；没有通用规则编辑/业务批准合同。[DR-0051](../decisions/DR-0051-tc15-source-derived-ux-prioritization.md)
- **测试反例**：将频率从略低于 3% 改为恰好 3%，冲突必须出现；点击普通证据确认不能消除规则冲突；生成 CSV 不得显示“生产界面已优化”。

### C05 上线报告生成成功，但业务检查结果是不得上线

- **任务与触发事实**：以 pm-014 的 PRD、配置、功能测试与兼容性材料核对发布；两份隔离成果通过来源/公式/结构验证，但来源推导的正式上线 Gate 未通过。
- **Agent 可继续 / 必须停止**：继续交付可审查报告、逐功能台账和整改依据；不能把“文件检查通过”投影为“允许上线”，更不能执行生产发布或修改配置。
- **用户动作与前台落点**：在现有成果区域并列显示“文件已生成”和“当前材料不满足上线条件”，可查看具体 Gate 的分子、分母、阈值与来源；不提供“确认仍然上线”的假按钮。
- **恢复与依赖影响**：材料修订后在批准来源版本下重新核对；历史报告保留，旧结果不能冒充新版本证明。当前没有发布 Connector，所以“不得上线”是检查结论，不是已经拦截了真实部署。
- **已有 / 待实现**：已有 `business_gate_outcome` 与 Artifact 验证双状态；无发布执行器、发布审批权管理和生产拦截。[DR-0043](../decisions/DR-0043-tc11-derived-release-gates.md)
- **测试反例**：相同 `verifier_status=passed` 下令一个正式 Gate 失败，首屏不得全绿；辅助通过率再高也不能替代正式 Gate；风险数量必须随来源变化。

### C06 委托书有律师证号，却没有可核验的登记回执

- **任务与触发事实**：核查 Legal-020 的六份委托书；某文件存在律师证号，但当前没有 Registry/Connector 回执可验证；另有文件可能连证号也未提供。
- **Agent 可继续 / 必须停止**：分别保留“已发现字段”“缺少字段”“真实性不可核验”；可生成风险台账，不能推断持证真实、授权有效或可签署。
- **用户动作与前台落点**：现有法务成果页保持确定性检查、业务 Gate、签署/人工复核三层。需要法务人员通过获准渠道核验；查看人不能用普通确认替代专业复核及组织权限。
- **恢复与依赖影响**：当前可保留未核验台账并停止放行结论；未来核验材料接入需来源与回执合同。不能将未接入的外部证明上传/验证流程写成现有入口。
- **已有 / 待实现**：已有 `unverifiable` 与触发/未触发分离，六文档字段隔离和人工复核标志；未实现登记验证、签署、授权生效或生产身份。[DR-0044](../decisions/DR-0044-tc07-source-derived-legal-delegation-review.md)
- **测试反例**：只填入形式正确的证号仍不可变绿；甲文件的证号不得用于乙文件；用户勾选“看过了”不得成为签署真实性证据。

### C07 三条工作线中一条 Worker 出问题，不能把整项任务推倒重来

- **任务与触发事实**：分别核对产品上线、搜索 Agent 运行、用户交互，产生五单元依赖图。搜索分支出现引用歧义，另两条贡献已采用；或某次 Worker 调用在重启后没有确认返回。
- **Agent 可继续 / 必须停止**：保留已采用贡献、旧成果和不依赖失败分支的状态；只阻塞真实依赖项。不能把“返回”当“采用”，也不能为未知在途调用自动重放或无限增兵。
- **用户动作与前台落点**：在原 Adaptive Swarm 中看“可用结果、受阻工作包、为什么受阻”；通过现有核对或获准恢复入口处理目标项。不给用户逐个 Worker 私聊，也不把内部 reservation 字段当默认说明。
- **恢复与依赖影响**：checkpoint 恢复单元须用当前版本、新幂等键显式重试，增加 attempt 并保留旧 Contribution；普通失败仍遵守它自身的恢复合同，不因本案例获得额外重试权限。依赖采用状态由服务端更新。
- **已有 / 待实现**：已有 Branch 绑定 WorkUnit、不可变 Contribution、最多三 Worker、局部保留及 checkpoint 恢复；当前是进程内只读，不是远端执行器。五单元案例的输出是逻辑 ArtifactVersion，不能宣称已生成新的 DOCX/CSV。[DR-0055](../decisions/DR-0055-durable-workunit-and-contribution-ledger.md)
- **测试反例**：修复搜索分支时其他已采用贡献不得重新调用或覆盖；只有依赖搜索结果的下游受阻；单纯调用重启不能让历史成果消失或自动再次消费模型预算。

### C08 用户说“把报告发给客户”，现系统只能到内部成果为止

- **任务与触发事实**：已形成跨职能风险简报后，用户要求发送客户、写入 CRM 或承诺发布日期。任务意图清楚，但这些动作不在当前 Runtime 能力/授权合同内。
- **Agent 可继续 / 必须停止**：可保留和展示现有内部成果；仅在现有支持范围内形成内容提案。必须明确“未发送、未写 CRM、未对外承诺”，不能用聊天里的口头确认突破 `external_action=none`。
- **用户动作与前台落点**：原成果区域说明能力边界及真实可用的查看/下载入口，由有权人员在系统外完成后续工作；不显示可点击的假发送入口，也不声称已自动转交给真人。
- **恢复与依赖影响**：当前不存在外发恢复。未来若接入，授权应绑定收件人、附件内容版本和动作，变更须失效；未知回执先查同一动作而非重发，内部版本恢复不能撤回已发邮件。
- **已有 / 待实现**：已有只读边界和有限隔离产物；身份、组织审批、外部授权、Connector 幂等/对账与真实补偿均待独立评审。[当前 API](../API.md)、[DR-0062](../decisions/DR-0062-dynamic-boundary-design-experiment.md)
- **测试反例**：填写收件人只解决内容信息，不生成发送权限；未来测试中把附件改后又改回不能复活旧批准；回执超时不能显示“未发送，可以重试”。后两项是未来合同测试，不是现有 Runtime 通过项。

## 4. 论文发现如何转成项目规则

## 5. 怎样融入原页面，而不是另做一套演示

1. **任务进展保留一个当前处理区**：用已有 Snapshot 说明“已有成果 / 哪一项需要处理 / 为什么 / 本次动作后果”。正常步骤继续简洁显示；未形成服务端事实的覆盖检查、业务批准和外发状态不能前端编造。
2. **处理入口按问题分流**：Agent 定位失败进入单 Branch 重试；多候选进入原 EvidenceReviewDialog；业务规则冲突和不可核验进入现有领域成果审查，明确仍需人工而非假装已有批准合同。
3. **处理后回到同一任务**：Loop 展示新 Run/版本及重核原因，Swarm 展示保留贡献与真实受阻依赖。不能以统一“已处理”掩盖决定已记录、执行尚未开始或回执未知。

对应现有前端是 [HarnessWorkbench](../../apps/web/app/harness-workbench.tsx) 的进展、执行记录、协作与领域成果投影；协议见 [UI-server fact matrix](../contracts/UI_SERVER_FACT_MATRIX.md)。这里是设计建议，本文件没有修改这些组件或协议。

## 6. 验收不能只问“能不能点”

先使用 [既有理解测试协议](../reports/copilot-boundary-design-20260911/comprehension-protocol.md)，在正式招募前冻结版本与任务，避免看到结果后改成功定义。每例先不讲解，记录用户第一回答：

- 现在什么已经做成了，什么还没有？
- 为什么需要我，还是其实应该由 Agent 自己补做？
- 点这个动作会改哪里、保留哪里？会不会修改原文件或对外执行？
- 依据变了、响应未知或我选择暂缓后，系统能否自行继续？

记录正确理解、误放行、误拒绝、把正确项改错、主持人提示次数、包含阅读与配置的总时间。另行验证版本冲突、候选无预选、幂等重试、依赖范围、结果/业务双状态和原文件不变。自动化能覆盖状态合同，不替代未参与设计的办公人员研究。

**本轮验证范围**：读取 living docs、相关 Decision 和既有失败 Evidence；定向复核当前输入截断、`external_action=none`、成果业务状态和 Worker checkpoint 文案源码；重新打开上述一手论文，并沿用有范围的原文核验台账。没有运行浏览器、模型、Runtime、数据库、真实外部动作或真人理解测试。历史测试数量不计入本轮，新增建议均未因本文件而升级为已实现。
