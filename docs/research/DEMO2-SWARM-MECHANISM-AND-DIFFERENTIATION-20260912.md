# Demo2：蜂群如何工作，差异究竟在哪里

日期：2026-09-12。定位：当前源码审计与可证伪差异设计，不是新颖性认定或竞品性能实测。

## 1. 先给一个准确名字

当前 Adaptive Swarm 是**有主控、有来源边界、有依赖关系的受限只读多 Agent 编排**，属于 orchestrator-worker 结构。不是去中心化涌现群体，不是多个聊天人格互相讨论，也不是分布式 Worker 平台。

Agent Control Loop 是推进同一任务的时间底座；Swarm 是其中一个受服务端准入约束的执行组织方式。只有合适的独立工作包才进入 Worker 路线，不是每个任务都强行多 Agent。

## 2. 一项任务怎样走完

以“分别核对产品上线、搜索 Agent 运行和用户交互，汇总跨职能风险”为例。以下五工作包是演示实例，**实际图必须来自服务端计划，不是固定编入产品的模板**。

```text
用户任务
  -> Planner 提出本轮工作包与批准来源
  -> 服务端校验计划、来源、依赖、预算、副作用
  -> Topology Admission 选择组织方式并给出原因
  -> 用户确认本批只读 Worker
       A 产品上线核对    B 搜索 Agent 风险    C 用户交互评估
                              |
                              v
                         D 风险影响分析
                  A、C、D 的已采用结果
                              |
                              v
                         E 跨职能汇总
  -> 每份返回先作贡献候选，通过采用门后才进入逻辑成果新版本
```

这是一张示意依赖图，不是当前运行的并发证据。第一波最多三个进程内 Worker，可以在同一进程以异步方式并发调用；后续工作包是否 ready 由服务端依赖状态决定，新的波次仍需明确确认。

| 步骤 | 谁拥有事实 | 用户可以观察到什么 | 不应误解为 |
| --- | --- | --- | --- |
| 拆分 | 模型提案，经服务端验证后形成 Branch | 工作包目标、批准资料、依赖 | LLM 自行获得任意权限 |
| 准入 | 确定性 Topology Admission | 单主控 / 固定流程 / 受限协作及原因 | 学习到的最优调度器 |
| 派发 | 版本化确认、预算预留、1-3 个 ready Branch | 本批范围、剩余调用预算 | 全任务永久授权、递归增兵 |
| 执行 | 进程内只读 handler | called、elapsed、返回状态 | 节点动画证明已经调用 |
| 采用 | 来源、Anchor、适用的叙事对账门 | returned 与 output_used 分开 | 多数投票就是真实，位置正确就是结论正确 |
| 汇合 | WorkUnit/Contribution 与普通 ArtifactVersion/TaskCommit | 已采用、待核对、被拒绝、版本变化 | Worker 一返回就自动写入最终答案 |
| 局部失败 | 服务端 Branch/依赖及恢复合同 | 保留其他贡献，只处理目标项 | 自动重放所有调用、自动撤销外部动作 |

源码：[topology_admission.py](../../services/api/app/application/topology_admission.py)、[readonly_workers.py](../../services/api/app/application/readonly_workers.py)、[harness_runtime.py](../../services/api/app/application/harness_runtime.py)。合同：[DR-0053](../decisions/DR-0053-durable-task-lineage-and-explainable-topology-admission.md)、[DR-0055](../decisions/DR-0055-durable-workunit-and-contribution-ledger.md)。

## 3. “Adaptive”目前具体指什么

`admit_topology` 使用已验证工作包、来源结构和剩余预算，而不是模型自己报“我需要更多 Agent”。

- 少于两个独立根工作包：单一主控。
- 有副作用意图或工作包需要 human gate：固定工作流。
- 独立根工作包超过三个：当前保守规则选择固定工作流，不无限扩编。
- 本轮至少三份来源且结构指纹相同、所有来源同属一个已知冻结来源组，或已提供 `source_facts` 但组信息不完整：固定工作流。这里是当前规则的具体条件，不把未提供来源事实的调用也描述为同一个分支。
- 调用预算不足以覆盖独立工作包及保留调用，或剩余 active 时间不足 20 秒：固定工作流。
- 满足当前条件才建议受限只读 Worker；明确确认后派发 ready Branch。

上述规则按顺序匹配。这些阈值是**现有保守实现规则**，尚未通过任务分布实验证明最优。`dependency_parallelism` 是派生结构字段，不是实测同时运行的 Worker 数；`TopologyAdmission.remaining_model_calls` 表示准入计算时的值，不冒充随调用扣减的实时余额。拓扑由任务结构约束不等于系统能解决任意复杂依赖；当前仍需 Planner 正确发现工作。

## 4. 哪些不能称为创新

“主控拆任务、Worker 分头做、主控汇总”已经是常用结构。LangGraph 官方文档直接提供 orchestrator-worker 与 `Send` 的动态 Worker 模式。[官方文档](https://docs.langchain.com/oss/python/langgraph/workflows-agents#orchestrator-worker)

Anthropic 的多 Agent 研究系统也采用主控与子 Agent，讨论了独立任务适配、成本、可观察性和恢复；其 2025-06-13 文章中的同步执行方式说明，“按波处理”本身也不能算我们的独占能力。[官方工程实践](https://www.anthropic.com/engineering/multi-agent-research-system)

因此目前**没有足够依据宣称一个新蜂群算法**，也不能说竞品不支持引用、暂停、持久化或人工参与。论文/产品未介绍某项保证，不等于它没有。

研究方面，[Intelligent AI Delegation](https://arxiv.org/abs/2602.11865)（Tomašev、Franklin、Osindero，2026-02-12 v1）把委派描述为不仅分配任务，也涉及权限、责任、角色边界和信任机制的决定序列。初稿核验摘要与元数据；2026-09-12 后续已追加框架、4.7 权限与 4.8 可验证完成的定向阅读，仍不是全文精读或复现。由此得到的项目设计推论是：Demo2 说明“分给谁做”，Demo3 还必须说明“分给了什么范围的决定权”；当前只读 Worker 确认不能当成通用业务权限转移。这个问题域已有研究，不应包装成本项目独占概念。

新增的 [Agent 机制论文选读](DEMO3-AI-AGENT-BOUNDARY-LITERATURE-20260912.md) 将该文与 MAST 的多 Agent 失败分类、Magentic-UI 的人类介入架构配对：分别用于约束委派、设计错误交接反例和比较原系统整合方式。这里只补研究依据，没有证明这些机制已经接入或现有蜂群取得性能提升。

## 5. 值得拿出来验证的工程差异候选

重点不是让更多 Agent 发言，而是把“贡献什么时候有资格进入长期办公成果”做成服务端合同。

| 差异候选 | 用户能看到的价值 | 当前证据 / 尚缺证据 |
| --- | --- | --- |
| 任务结构与来源约束共同决定是否分工 | 为什么这次协作、另一次不协作有可查原因 | 准入规则及正反例已有；尚无成本/质量最优性对照 |
| 候选贡献与正式采用分离 | 三个 Agent 都返回，仍可能只有两份进入成果；坏引用不能混入简报 | 来源越权、无 Anchor、歧义、冲突叙事的拒绝/保留测试已有；不能保证语义正确与全文覆盖 |
| 局部恢复和同 Task 不可变历史结合 | 修一个分支不丢其他成果，知道新版本改了哪一部分 | Branch continuation、WorkUnit 台账、checkpoint 合同已有；本轮未重跑真实数据库/Provider 联合恢复 |
| 权限和执行状态用业务语言展示 | 用户知道是在选依据、允许计算，还是面对未获准业务动作 | 本轮在原能力页增加解释投影；尚无目标用户理解/误批准改善证据 |

这些可以称“原生保证的组合差异”或“可证伪候选”，不能直接升级为领先竞品、独创机制或用户收益。

## 6. 应该怎样演，而不是只展示一张图

1. 同一任务先看准入：列出三个独立根工作包、来源和本批预算；没有确认，不出现已调用事实。
2. 首批返回后故意保留一条歧义贡献：界面显示三条已调用、两条已采用；查看哪个下游依赖该分支。
3. 只处理出问题的分支：展示决定/继续回执，核对旧贡献不重新调用，旧成果不被覆盖。不同恢复类型严格走自身合同，不强行统一成一个按钮。
4. 形成新版本：比较旧版与新版，并指出新增内容仍需业务复核。图节点完成不代替结果检查。
5. 反例再演一次：只有一个独立工作包或不满足预算，系统选择单主控/固定流程，不为了展示蜂群而硬开 Worker。

上述状态可以用原系统的受控 API fixture 回归；这证明前端处理指定合同状态，不是现场真实模型生成这些结果。真实模型演示另列预算、来源版本、Run/Worker 回执和失败，不用 fixture 图冒充。

## 7. 证明价值还差什么实验

冻结相同任务、来源版本、Provider 配置、总预算及评分口径，比较：单主控、普通 fan-out/fan-in 基线、当前受限协作。简化采用门的对照仅在隔离实验中实现，不关闭正式系统保护。

在固定正常任务之外，注入一个 Worker 引用越权、一个来源歧义、一个真实依赖失败、来源变更、一次持久化后中断。至少记录：

- 错误贡献进入最终成果的比例、正确贡献被误拒绝的比例。
- 未受影响分支的重复调用数、恢复额外调用/时延、旧成果保留情况。
- 最终需求覆盖和业务质量，不能只数引用及 Artifact 是否存在。
- 用户对“已经做了什么、下一步后果”的理解，误批准、误拒绝及包含阅读的总用时。

当前未完成这些同场对照，故不报告节省百分比、能力提升百分比或统计显著性。本轮实际 Runtime 单元回归为 `tests/unit/test_demo2_runtime.py` 的 22 项通过；不是远端 Worker、生产沙箱、真实模型质量或数据库恢复的新证据。
