# 人机共驾设计指导手册

办公 Agent 的边界规则、协作方式与案例参考

版本 1.0 · 修订于 2026 年 9 月 19 日

## 使用这本手册

办公 Agent 可以整理资料、起草内容，也可以代用户向其他人发送信息、创建任务或修改记录。设计这些功能时，需要逐项确定它能做到哪一步，以及用户在什么地方参与。

这本手册供产品与交互设计人员使用。它从安全、效率、透明度和接管四个方面讨论办公中的人机分工，提供风险与接管方式的对应表，并用案例说明界面应如何变化。配套的[《边界情形与接管案例库》](边界情形与接管案例库_v1.0.md)可以按风险等级、介入原因或交互方式查找。

设计一个新功能时，先写清它将改变什么，再找相近案例。案例中的默认处理方式可以作为起点；具体权限、数据范围和审批要求，需要结合所在组织的制度确定。这里的 L0 至 L5 是用于产品设计的分级约定，不能替代组织自身的风险分类。

## 1. 从具体动作判断边界

“帮我完成客户汇报”包含查资料、写报告、核对内容、发送邮件等不同动作。前面的资料整理可以连续进行，发送前则需要核对收件人、正文和附件。同一任务中的自主程度会随动作变化。

设计师可以用以下问题描述一个动作。遇到信息不全的地方，应在交互中给用户一个具体的补充入口。

| 判断内容 | 要查清什么 | 对设计的影响 |
| --- | --- | --- |
| 动作和对象 | 做什么，作用于哪个文件、记录或人 | 预览中显示完整对象，避免只写“已处理” |
| 数据流向 | 使用什么资料，在哪里处理，交给谁 | 在读取和传送前检查权限；外发前说明敏感内容 |
| 状态变化 | 生成草稿，还是修改已有业务记录 | 草稿与提交使用不同按钮和结果提示 |
| 影响范围 | 仅本人、团队、外部联系人或批量对象 | 范围越大，越需要提前展示受影响对象 |
| 恢复能力 | 能恢复哪些内容，哪些影响无法收回 | 只有实际支持恢复的操作才显示“撤销” |
| 意图和证据 | 联系人、版本、日期是否明确，材料是否冲突 | 缺信息时澄清；有冲突时请用户作判断 |
| 权限和制度 | 谁可决定，是否需要审批，哪些动作受限 | 缺授权时停在准备阶段，显示可办理的下一步 |
| 使用环境 | 屏幕、设备和会话状态是否足以完成核对 | 手机保留关键预览，必要时保存待办并转到桌面 |

环境信息必须有来源。系统不知道用户是否在公共场所时，不应声称已经检测到，也不应为此默认启用录音或摄像。

## 2. 四类边界怎样影响设计

四类边界分别回答四个问题：系统是否有条件行动，哪些工作值得交给它，用户能否看清当前情况，以及何时、如何把控制权交还给人。同一动作往往同时涉及几类边界。例如，向客户发送报告既有资料和授权要求，也涉及核对成本、发送状态与异常恢复。

下文将研究发现与设计建议分开表述。表中的判断项用于组织设计讨论，不是已经经过验证的通用评分模型。

### 2.1 安全边界：哪些条件满足后，动作才可以发生

安全边界从接触资料时就开始生效。即使用户只要求起草一份报告，读取工资、合同或客户信息，传给云端模型，以及把结果展示在共享屏幕上，都可能带来不同影响。设计需要分别说明允许使用的资料、处理位置、可见对象和最终用途。起草权限不包含外发权限，能够打开文件也不代表可以把它传给任何处理服务。

近年来的 Agent 安全综述把风险扩展到工具、记忆、外部内容及多个 Agent 之间的协作。[19][20] 对办公产品而言，确认按钮只是其中一项控制。访问权限、动作范围和数据流向应先受系统约束，不能把所有风险交给用户在最后一屏发现。

#### 判断哪些情况必须停下来

| 条件变化 | 需要重新核对的事实 | 界面应如何回应 |
| --- | --- | --- |
| 个人副本变成共享正式文件 | 谁会受到影响，能否恢复，谁有权修改 | 显示具体文件和变更范围，重新确定确认要求 |
| 内部使用变成外发 | 完整收件对象、敏感内容、附件版本、批准条件 | 提供最终内容预览，将缺失条件放在确认按钮附近 |
| 单条处理变成批量操作 | 数量、筛选范围、例外项及最大可能影响 | 展示名单或样本与总量；不能仅用一条泛化提示批准整批 |
| 来源或指令不可信 | 请求来自用户、组织规则，还是待处理文件 | 文件中的指令保留为内容，不授予新的读取或执行权限 |
| 已批准内容发生变化 | 对象、正文、金额、附件、授权是否仍与原决定一致 | 说明变化，旧批准失效或进入重新核验 |
| 无法判断实际执行结果 | 请求是否被受理、动作是否已发生、是否存在原回执 | 标为结果待核对，保留查询路径，避免重复执行 |

AgentDojo 等研究把不可信内容与工具调用结合起来测试，说明只检查最后生成的文字不足以覆盖 Agent 风险。[13][14] 因而，设计评审还应追问：界面显示“未发送”时，系统是否确实阻止了发送？用户拒绝后，后续步骤是否仍可能访问同一外部对象？

#### 区分补信息、申请授权与明确受限

三种情况需要不同出口。联系人不明确，应请用户选择；缺少批准，应说明由谁批准、需要什么材料；动作被组织规则禁止，则应停止实施并保留允许的准备工作。“继续”按钮不能同时承担这三种含义。

确认页应绑定一个可辨认的动作：谁将收到哪份内容、哪些记录会改变、可能无法收回什么。核对内容很多时，可以按需要用户决定的事项分组，但每组应有独立范围。用户修改收件人后，需要重新核对外发对象；不能因为正文未变就沿用原确认。

《The 2025 AI Agent Index》记录了 30 个已部署系统，并指出开发者披露的安全与评估信息存在明显差异。[21] 这支持将权限、限制和结果做成可检查的信息，也提醒设计人员：厂商标注“有护栏”并不能证明具体动作得到保护。

在 C04 外发报告中，用户应先看见完整地址、正文与附件；遇到未获授权的价格承诺，则转入 C05 的受限处理。重要的检验是：是否阻止了未授权影响，用户能否理解停下来的原因，以及修改后能否从正确位置继续。对应 R01-R03、R07-R09、R15-R16。

### 2.2 效率边界：哪些工作交给 Agent 后，整体负担会更小

适合自动处理的任务通常有明确目标、相对稳定的输入、容易检查的结果，以及可接受的出错和恢复成本。资料去重、个人文本格式整理、已授权范围内的状态查询可以从这些条件出发。开放式判断、材料冲突或责任不明的任务，即使生成速度很快，也可能需要大量人工核查。

自动化层次研究区分信息获取、分析、选择与实施，Agent 综述则进一步讨论规划、工具使用和评估。[1][16] 因此，同一事项可以只自动完成其中合适的部分。例如，准备一封客户邮件可以自动整理材料与形成草稿，正式发送仍保留决定点。

#### 把核对和恢复时间计入效率

评估效率时，应同时记录用户下达要求、补充上下文、等待、阅读核对、纠错和恢复所花的时间。后台运行期间用户是否能处理别的工作，也应单独记录。较少点击、较快生成或较高采纳率，都不能单独证明整体效率更好。

Becker 等在早期 2025 年工具和特定熟练开发者任务中观察到耗时增加，而参与者主观上认为自己更快。[28] 该结果受工具时间点和任务条件限制；METR 在 2026 年的后续方法说明中又指出选择偏差和并行工作会妨碍可靠估计。[31] 这里需要吸收的是测量方法：区分感受与实际耗时，并在当前产品任务上重新验证。

| 任务条件 | 可考虑的协作方式 | 需要观察的成本 |
| --- | --- | --- |
| 范围清楚、低风险、可恢复 | 自动完成，事后查看和撤销 | 用户是否容易发现错误，撤销是否比手动重做省事 |
| 结果容易检查，但内容仍需判断 | 先给草稿和来源 | 阅读、定位出处及修订成本 |
| 少量事实缺失 | 在执行前集中澄清必要字段 | 反复追问次数，用户是否知道为何需要补充 |
| 已知规则内的内部变更 | 展示变化后普通确认 | 用户核对的内容是否真正影响决定 |
| 含冲突或专业责任 | 整理证据与选项，交给适当人员判断 | 交接准备、理解上下文与等待责任人处理的成本 |

#### 打断发生在能改变结果的地方

Horvitz 的混合主动交互研究强调行动、提问和注意力成本之间的取舍。[2] 在办公场景中，可以先准备不依赖用户决定的部分，再集中提出真正阻碍推进的问题。若用户只需从两个“王工”中选一位，就显示足以区分身份的信息，不要求重填整份任务。

历史表现可以影响提示方式，但不能自动扩大权限。Liu 等对 875 位门店经理的纵向研究发现，持续绩效评价与委托意愿之间存在反馈关系。[18] 对产品的设计推导是：允许用户查看和调整已授予的低风险委托范围；一次失败后可增加核对，但不能因多次接受建议就默认为用户同意新的外发行为。范围变化仍由安全规则处理。

C01 的个人整理应直接显示结果和撤销；C02 的资料准备应让来源核查方便；C06 的同名对象只提出必要澄清。评审既看节省了多少操作，也看返工、遗漏和被打断后恢复工作的负担。对应 R04-R06、R09、R11-R12、R14。

### 2.3 透明度边界：用户能否看清状态、依据和控制权

透明度首先服务于当前决定。用户要能判断：任务由谁推进，系统准备做什么，已经发生什么，依据是否可靠，自己现在能采取什么行动。把这些信息分开，才能避免“正在准备”“等待批准”和“已经完成”在界面上呈现为同一种进度动画。

Zhang 等对 134 篇人机共创研究的综述，将能动性配置与具体控制机制联系起来。[25] 这提示设计人员，控制权不能只写在功能介绍里，还要在操作时可辨认。相同页面中，“Agent 正在整理”“等待你确认”“你正在手动编辑”应对应不同的状态和可用操作。

#### 四层信息分别承担什么作用

| 信息层 | 用户需要回答的问题 | 合适的内容 |
| --- | --- | --- |
| 当前状态 | 现在谁在推进，是否需要我处理 | 执行、等待、人工编辑、已停止、结果未知等明确状态 |
| 决策依据 | 我凭什么接受或修改这项建议 | 原文位置、字段差异、来源版本、不确定项与冲突 |
| 执行结果 | 到底改变了什么 | 受影响对象、实际回执、失败范围、仍未发生的动作 |
| 操作历史 | 出现问题后怎样追查 | 内容修订、当时的决定、执行与恢复记录，按权限展示 |

首屏应放当前状态及影响决定的内容。完整收件地址、金额和版本属于核对材料，不宜为了页面简洁全部折叠。技术过程可以放入详情，但用户打开详情后应能回答一个具体问题，而不是面对未经整理的日志。

#### 解释要便于验证，并说明局限

解释研究给出的结果并不一致：解释可能帮助理解，也可能增加对错误建议的接受；降低验证成本是重要条件。[7][8][9][10] 因此，“为什么这样建议”最好紧邻原文或差异，让用户有条件检查。对不确定内容，应指出缺少哪项资料或哪一处存在冲突；没有经过校准的概率依据时，不显示貌似精确的置信百分比。

Feng 等对 Agent 界面模式的研究同时讨论了过程展示的真实性和信息粒度问题。[24] 设计上应优先呈现可核查的计划、动作、证据与回执。模型生成的理由只能作为说明，不能当作内部运行过程或执行成功的证明。

Glassberg 等在 118 位组织参与者的模拟工作情境中研究了信息透明度、视觉设计与信任的关系。[26] 这为信息组织提供了经验线索，但不意味着增加说明或改善视觉就能减少误操作。评审仍需观察用户能否发现错误、区分草稿与正式提交，以及在证据不足时拒绝建议。

C02 可以把摘录与来源并排放置，C08 应显示版本变化，C09 应明确“请求已发出，结果仍待核对”。手机端采用纵向阅读也应保留这些信息，不能用颜色或“处理成功”四个字取代。对应 R05-R06、R08-R09、R13、R16。

### 2.4 接管边界：何时交还控制，以及如何让人接得住

接管既可以由系统发起，也应允许用户主动提出。触发原因包括缺少关键事实、材料冲突、超出权限、结果校验失败、连续重试无进展，或任务已偏离用户目标。接管的形式可以是回答一个问题、作业务选择、手动完成一段操作，或停止整个事项，不必每次都把整项工作重新交给用户。

Tomašev 等提出的委托框架将角色、权限、结果可验证性和环境变化纳入持续协调。[23] 这是概念框架，具体阈值仍需在产品中定义。比如“连续失败几次后停止”要结合操作成本和可能影响确定，不能把统一次数用于所有任务。

#### 接管前保留足够的工作现场

Bainbridge 对异常处理的讨论和情境意识研究说明，人需要重新理解现场，才能承担关键决定。[4][5] 系统停下时，应让用户知道已经完成的部分、最后可靠状态、当前阻碍、尚未执行的动作，以及接下来需要决定什么。

| 介入原因 | 用户需要完成的工作 | 交接内容与去向 |
| --- | --- | --- |
| 信息缺失 | 补齐对象、日期、版本等事实 | 一个具体问题和可核对候选；答复后仍执行原有授权检查 |
| 业务判断 | 处理冲突、例外或专业问题 | 并列证据、可选处理及影响；交给有责任和能力的人 |
| 执行授权 | 决定是否实施当前动作 | 最终对象与内容、权限和恢复范围；允许修改、暂缓、拒绝 |
| 执行异常 | 核对实际结果，选择恢复办法 | 已知结果、未知部分和原请求；避免重新执行已完成动作 |
| 用户主动接管 | 改变目标或手动处理当前步骤 | 当前工作副本和进度；明确 Agent 哪些操作已经停止 |

#### 暂停、手动处理与恢复需要连续设计

用户点击停止后，应先显示停止请求是否已收到，再说明是否仍有在途动作。若发送已经被外部系统受理，停止后续步骤不能写成“邮件已撤回”。取消、恢复草稿和补救外部影响应使用不同名称。

Feng 等区分了中断和直接接管，并指出在途动作与回滚是控制转移中的设计难点。[24] 这对应一项具体要求：人接手之后，Agent 不应同时继续改同一份内容。用户完成手动处理后，应重新核对目标、内容版本和剩余授权，再决定是否恢复自动推进。

找不到合适责任人，或用户暂时无法核对时，可以保留待办并保持安全暂停。等待超时不表示批准。移动端离开页面后，再次打开要确认内容是否变化；敏感动作不能凭一声脱离上下文的语音“好”继续执行。

#### 监督本身也需要能力和时间

Dhanorkar 等在 2026 年对 17 位开发者的访谈中区分了事前限制、共同规划、实时监控和事后审查，显示监督分布在整个工作过程中。[29] Mitchell 等同年的立场文章进一步提醒，设计需要支持监督者的注意力和专业判断，而不能只安排一个人点击批准。[30] 后者是风险论证，并非本产品已有的效果证据。

因此，较复杂或高后果任务应留出理解上下文的时间，允许用户标记“无法判断”并转交合适人员。评审应观察用户能否在接管后准确说出当前状态、完成关键决定，以及恢复时是否重复或遗漏工作。C07、C11 用于业务判断，C09 用于异常恢复，C12 用于移动端暂缓；对应 R04、R07、R09-R11、R13-R16。

## 3. 风险等级与接管方式

下表给出默认对应关系。风险等级描述动作影响；接管方式还取决于当前是否缺信息、缺权限或发生异常。因此，一个 L4 外发动作可能先澄清联系人，再核对内容，最后取得批准。

| 等级 | 典型情形 | 默认协作方式 | 用户接管时点 | 设计重点 |
| --- | --- | --- | --- | --- |
| L0 无业务影响 | 已获准的状态检查、维护心跳 | 静默处理，状态可查 | 用户主动查看或关闭维护时 | 不占用注意力，不扩大读取范围 |
| L1 个人、低风险且可逆 | 整理个人草稿的格式 | 自动完成，提供撤销 | 结果不合意或操作范围变化时 | 改动可见，撤销可用 |
| L2 内容准备 | 摘要、备忘和回复草稿 | 展示草稿与来源 | 需要修订或准备正式提交时 | 编辑方便，保留不确定项 |
| L3 有限内部变更 | 为同事创建一条协作任务 | 普通确认后执行 | 改变协作记录之前 | 对象、字段和影响可检查 |
| L4 外发或敏感高后果动作 | 客户邮件、正式提交、敏感资料审查 | 准备或强确认；按制度取得审批 | 敏感处理或正式实施之前 | 内容、依据、权限和影响一起核对 |
| L5 极高风险或受限动作 | 无权作出的价格承诺、受限权限变更、重大批量删除 | 停止自动实施，交给有权人员或正式流程 | 发现受限条件时 | 解释限制，保留允许的准备工作 |

几个容易混淆的地方需要在产品定义中说清：

- 外发邮件无法保证完全收回，但通常可以在满足制度要求后归入 L4。不可逆性是判断因素之一，具体等级还要看影响范围与组织政策。
- 敏感资料即使只生成内部草稿，也可能需要较高等级的访问和处理约束。财务异常核查可以采用 L4 的数据要求，同时只允许起草意见。
- 取得新审批后，应根据新事实重新评估动作。原来被拒绝的版本仍保留拒绝记录。

### Agent 可以参与到哪一步

AL 表示自主程度，用于设计讨论。它与风险等级分别记录，不按数字大小直接换算。

| 自主程度 | 允许范围 | 常见产品呈现 |
| --- | --- | --- |
| AL0 观察 | 展示允许查看的状态 | 状态面板 |
| AL1 建议 | 提醒和处理选项 | 建议卡 |
| AL2 草稿或模拟 | 准备内容，供用户检查 | 可编辑草稿、预览 |
| AL3 确认后执行 | 对当前动作取得有效确认后实施 | 确认卡及执行回执 |
| AL4 可撤销自动执行 | 在获准范围内完成低风险操作 | 结果提示及撤销入口 |
| AL5 静默后台 | 无业务影响的维护 | 必要时可查的维护记录 |

AL5 只适用于表中所述维护范围。数据读取权限仍然适用。

## 4. 可复用的设计规则

以下编号供手册与案例库交叉查阅。

### R01 至 R05：任务开始和内容准备

R01 按动作说明授权范围。任务开始时让用户知道会读取什么、准备什么，以及哪些步骤需要再次决定。新对象或新用途超出范围时重新确认。

R02 在使用资料前检查访问和处理条件。打开、下载、传给模型、展示、外发各有不同影响。网页和文件里的指令应作为待处理内容，不能授予权限。

R03 受限动作按制度处理。赶时间、长期使用和历史采纳率都不构成新的授权。界面分别说明明确禁止、缺少材料和等待审批。

R04 对缺失信息提出具体问题。告诉用户缺哪一项，列出可核对的候选信息。联系人、金额、日期和版本缺失时，先补齐再推进。

R05 区分内容准备和业务提交。“保存草稿”“创建任务”“发送邮件”分别说明自己的结果。检查报告中的建议需要由有权人员决定如何处理。

### R06 至 R09：核对、确认和执行

R06 把核对依据放到动作旁边。提供相关原文、字段差异或内容预览，并说明来源能支持什么。引用存在只证明可以找到该材料，不能保证结论正确。

R07 让确认对应实际核对工作。普通确认侧重对象和字段；强确认还需要说明敏感内容、重要承诺、审批条件与不可完全恢复的影响。按钮直接写出动作，例如“确认发送这封邮件”。

R08 确认绑定当前版本。改了收件人、正文、附件、金额或权限后，先前的批准需要重新检查。旧页面应明确提示内容已经变化。

R09 结果不明时先核对。提交超时可能发生在动作完成之后。此时显示“结果待核对”，保留原请求，并提供查询入口；重复点击不能造成第二次业务影响。

### R10 至 R14：接管、恢复与长期使用

R10 交还控制时说明暂停原因、已完成内容和需要谁决定什么。用户应能暂缓，并在之后回到同一事项。

R11 把恢复范围写清楚。恢复一份草稿、撤销一次修改和补救一封已发邮件是不同操作。界面应按实际能力命名，已保留的成果继续可查。

R12 个人偏好需要明确范围和撤回入口。“以后不用问”可用于获准的低风险操作；新的收件人、敏感字段和高后果动作仍应重新判断。

R13 手机端保留决定所需的信息。地址、金额和附件版本应可完整查看。信息不足时允许保存待处理或转到桌面；语音“好”需要对应到当前动作和身份。

R14 撤销应有实际恢复能力。说明哪些内容可以恢复、期限是什么，以及哪些已发生影响无法收回。撤销失败时保留记录并给出后续处理方法。

### R15、R16：支撑界面承诺

R15 产品显示“可以执行”之前，应由可信的权限、业务规则和当前内容共同支持。模型可以提出建议，实际执行范围由系统约束。

R16 为重要动作保留可追查的记录，包括提议内容、修改、决定、执行结果和恢复情况。记录按访问权限展示，并控制敏感原文的保存范围。

## 5. 交互模式与页面安排

### 自动处理和草稿

自动整理完成后，用一条简短提示交代变化，并提供查看和撤销。草稿可放在正文工作区，来源就近展示。用户继续编辑时保留来源关系，丢弃草稿不影响原材料。

### 澄清和业务判断

澄清适合小范围的信息补充。一个问题能解决的，不必展开整页风险说明。业务判断通常需要更多空间，可用并排对照展示冲突材料和处理选项。

对于容易被建议影响的重要判断，可以试验“先看证据、形成初步选择，再查看 Agent 建议”的顺序。是否采用这种方式，应观察错误发现率和额外耗时，避免给日常低风险任务增加无关负担。

### 普通确认和强确认

普通确认卡包含动作、对象、可编辑字段和结果说明。强确认需要更完整的内容预览，外发场景至少能查看全部收件地址、正文、附件版本、敏感内容与批准条件。修改和取消入口应与确认同样容易找到。

Risk Lens 可以作为这组信息的展开视图。首屏说明暂停原因和下一步，展开后查看证据、影响与规则。设计时应优先放置用户当前要核对的内容。

### 受限处理和执行异常

受限卡说明不能执行的具体原因，以及仍可以办理的事项。若只能打开审批入口，应写“打开审批”，直到正式系统确认受理后才能显示“已发起审批”。

执行异常应保留用户刚才核对的内容。明确失败时可以提供受控重试；结果未知时先查询实际状态。关闭页面只退出当前视图，不能被解释为批准。

| 页面操作 | 应产生的含义 |
| --- | --- |
| 暂缓 | 保留待处理事项，目前不执行 |
| 取消本次动作 | 结束本次意图，保留已有成果 |
| 拒绝 | 记录不批准这个动作或方案 |
| 停止 | 停止后续推进，并说明生效位置 |
| 撤销 | 恢复实际支持恢复的内容 |
| 关闭 | 离开视图，保留尚未决定的事项 |

## 6. 用案例检查设计

设计评审可以从配套案例库选择不同协作方式，再改变一个条件观察交互是否跟着变化。例如，“整理个人草稿”改成“修改共享正式文件”，或“发送已核对报告”改成“附件刚刚更新”。条件变化后的范围、状态和操作应保持一致。

评审时请参与者指出 Agent 已经做了什么、当前需要自己决定什么、确认后会发生什么。记录误解出现的位置，并核对完成时间、错误发现、误批准和恢复情况。只统计点击量或满意度，难以发现用户误把草稿当成已提交的情况。

风险识别可使用由业务人员事先裁定的案例集；还应单列信息不明、授权变化、重复提交和响应丢失等异常。财务、合同和权限类测试使用合成材料与测试环境，研究过程不产生真实业务后果。

## 7. 理论依据与设计取舍

本手册以经典自动化与人机交互研究解释基本问题，结合 2025-2026 年的 Agent 研究讨论新的委托、工具调用和监督条件。文献中的研究发现、作者提出的框架，以及本手册据此形成的设计建议，分别对待。L0-L5 分级和具体按钮安排属于产品设计约定，需要结合组织规则与任务测试验证。

### 7.1 自主程度应随动作和条件变化

Parasuraman 等的自动化类型与层次模型，为区分信息处理和动作实施提供了基础；Horvitz 的混合主动交互讨论了什么时候行动、什么时候向人提问。[1][2] Lou 等的人机团队综述把协调、共享理解和责任分配纳入讨论，近期 Agent 架构综述也将规划与实际动作区分开来。[17][27]

本手册据此采用逐动作的判断方式：整理、起草、修改共享记录和外发分别定义允许范围。Agent 当前可以自主推进到哪一步，会随对象、影响和权限变化。设计者需要让用户看见这些变化，并能在相应步骤调整范围、核对内容或收回控制。

### 7.2 委托习惯可以调整提示，授权仍需明确

Liu 等的纵向研究表明，绩效评价和委托意愿会相互影响。[18] 这支持在长期使用中关注用户是否反复收回任务、纠正同类错误或希望减少低风险打断。Tomašev 等则把权限和责任纳入委托框架。[23]

设计取舍是将偏好与授权分开：记住用户喜欢怎样整理草稿，同时让用户能查看和撤回这项偏好；新的收件人、敏感用途或正式承诺仍重新核对。不能把“过去经常接受”推导为“以后任何相近任务都可以代办”。

### 7.3 把安全要求落实到动作与资料流向

TRiSM 和 Agent 安全综述讨论了工具、隐私和持续治理；AgentDojo、Agent-SafetyBench 提供了含工具和不可信内容的评估视角。[13][14][19][20] AI Agent Index 则是部署现状与披露情况调查，不是产品安全效果实验。[21]

对应的设计是把读取、传送、修改与外发的范围说清楚，让受限条件在影响发生前可见，并保留拒绝与异常路径。普通确认、强确认和禁止实施分别解决不同问题。一次确认也不能使组织禁止的动作变得合法可做。

### 7.4 透明度以可核查和适当依赖为目标

Lee 与 See 的研究强调适当依赖；后续解释研究说明，解释的作用取决于呈现方式、任务及验证成本。[3][7][8][9][10] 共创研究中的控制机制分类、组织情境中的设计与信任研究，则为页面组织提供了补充视角。[25][26]

本手册选择分层展示状态、证据、结果与历史。对重要建议提供原文和差异，对未知事实保留未知。Feng 等提出的界面治理模式支持把可见性与实际控制能力联系起来，但其模式分析不能直接证明某个页面能降低错误率。[24]

### 7.5 接管设计要支持人的判断

传统自动化研究已经指出，异常时才把任务交给人，会使其面临较重的理解负担。[4][5] 《Fully Autonomous AI Agents Should Not be Developed》从价值与风险角度讨论限制自主性的理由；它是一篇立场文章，不是所有办公任务都必须逐步确认的实验证据。[22]

2026 年的实际监督访谈提供了更贴近当前工具使用的观察；关于监督能力的最新立场研究则提出注意力和技能维持问题。[29][30] 关于人机 Agent 沟通的研究报告也讨论了目标表达、共同理解和过程协调的困难。[11] 因此，本手册要求接管时保留工作现场，区分需要用户补事实、判断业务还是核对执行结果，并为无法判断的情况提供转交或安全暂停。

### 7.6 必要的核对负担要有可验证的作用

Amershi 等的交互指南支持能力说明、纠正、退出和谨慎适应；Magentic-UI 展示了共同规划与控制交还的原型方式。[6][12] 它们为可选交互机制提供参考，不能代替对本产品任务的测试。

Ghosh 等 2026 年的写作计划审查实验发现，检查关键假设的机制在其条件下较好地减少了过度依赖，而参与者觉得最有帮助的机制并不相同。[15] 设计上可在重要决定处试验具体问题，例如“这次价格是否已经批准”；不宜把多勾几个通用复选框直接当作更强的核对。

效率评估同时参考实际耗时和感受，并保留工具版本、任务难度与经验差异。[28][31] 检验边界设计时，除完成时间外还要看错误发现、误批准、接管后恢复情况，以及用户是否能准确解释当前状态。满意度和信任评分作为补充，不替代这些结果。

### 7.7 近期研究的证据类型与使用范围

| 文献 | 类型与研究对象 | 在本手册中的作用 | 不宜推导的结论 |
| --- | --- | --- | --- |
| Liu 等，2025 [18] | 875 位门店经理的纵向委托研究 | 讨论委托意愿的变化 | 历史表现可以替代授权 |
| Glassberg 等，2025 [26] | 118 位组织参与者的模拟工作情境研究 | 讨论信息组织、视觉与信任 | 页面更美观必然更安全 |
| Zhang 等，2025 [25] | 134 篇人机共创研究的范围综述 | 区分能动性与控制机制 | 每种工作流都需要相同可视化 |
| Chhabra 等，2026 [20] | Agent 安全综述 | 确定工具与外部内容的风险检查范围 | 一个确认框足以防住攻击 |
| Staufer 等，2026 [21] | 30 个部署系统的信息调查 | 关注安全特性与评估披露 | 功能披露等同于安全有效性 |
| Tomašev 等，2026 [23] | 委托与权限的概念框架 | 组织角色、范围与动态交接 | 已验证通用阈值或办公收益 |
| Ghosh 等，2026 [15] | 写作计划审查实验与后续质性研究 | 选择值得测试的核对机制 | 在所有任务上都能减少过度依赖 |
| Dhanorkar 等，2026 [29] | 17 位开发者的探索性访谈 | 理解监督发生的阶段与工作负担 | 所有办公人群都具有相同习惯 |
| Mitchell 等，2026 [30] | 监督与认知能力的立场文章 | 检查人的接管条件和长期负担 | 已证明本产品会造成技能衰退 |
