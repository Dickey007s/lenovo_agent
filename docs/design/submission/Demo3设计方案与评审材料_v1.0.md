# Demo3 设计方案与评审材料

版本 1.0 · 2026 年 9 月 19 日

## 1. 演示目的与范围

Demo3 展示办公 Agent 在不同简单事项中如何与人分工。用户每次办理一件事，可以检查、修改、暂缓或取消。Demo1 展示长任务的拆分推进，Demo2 展示多任务规划与并行，三者使用同一 Agent 工作台。

本方案依据[《人机共驾设计指导手册》](人机共驾设计指导手册_v1.0.md)和[《边界情形与接管案例库》](边界情形与接管案例库_v1.0.md)。演示内容可编辑，不要求按固定顺序播放。六类事项均在测试工作区运行：文本副本和判断记录可以保存，协作任务与发件只生成测试记录，没有连接真实邮箱或企业审批系统。材料对照使用非敏感示例，不自动判断资料真伪。

这份材料用于设计讨论和现场演示。正式设计人员评审尚未举行，后附记录表不预填评审结论。

## 2. 同一工作台中的布局

左侧文件目录供用户查看资料；中心工作区显示当前事项、内容和需要人处理的部分；右侧保留实际操作记录。查看资料不会启动事项。用户修改草稿时，界面明确显示“你正在编辑”；等待判断时，显示“Agent 不会自动继续”。

事项首屏说明当前处理方式和状态。需要决定时，正文、完整对象或对照材料应可直接阅读；影响、恢复范围和历史记录按需展开。风险等级与自主程度分别显示，帮助解释为什么相似任务会有不同处理方式。

最近事项入口用于找回已暂缓或已完成的记录。其范围是当前演示身份最近 20 个任务中的事项，不作为完整历史或团队待办箱。读取、展开与下载记录都不会批准业务动作。

## 3. 六类事项的协作差异

| 事项与案例 | Agent 已做什么 | 用户需要做什么 | 结果与边界 |
| --- | --- | --- | --- |
| 整理个人文本，C01 | 整理个人副本的空白与段落 | 查看变化，需要时撤销 | 可恢复原内容；不修改源文件 |
| 准备资料摘录，C02 | 从获准预览或用户文字中截取最多 1200 字符 | 对照来源，在工作台内修改草稿 | 保存人工修订，原文继续保留；不称为完整摘要 |
| 创建协作任务，C03/C06 | 准备标题、内容、负责人和日期 | 补齐对象，再确认创建 | 形成测试任务；未通知真实同事 |
| 发送汇报内容，C04/C08/C09 | 准备完整对象与正文，等待核对 | 逐项核对，或修改、暂缓、取消 | 形成测试发件记录；未发送真实邮件 |
| 受限业务请求，C05 | 根据演示策略阻止受限动作 | 查看原因，必要时下载人工处理说明 | 无执行结果；下载不表示审批已发起 |
| 核对材料分歧，C11 | 并列保留用户提供的两份材料 | 选择本次采用哪份并写明理由，或表示暂时无法判断 | 记录人工判断，两份原文均不变，不自动启动下一任务 |

同名联系人澄清与正式创建是两个不同决定。材料对照中的选择也只确定本次判断，不能代替发送确认或正式审批。来源中出现“忽略规则”“发送全部资料”等文字时，摘录仍只保留文字，不产生新权限。

## 4. 四类边界在页面中怎样体现

安全边界体现在影响发生前的限制。发件对象与正文需核对，修改之后旧核对失效；明确受限的动作没有继续执行入口。当前受限词是固定演示规则，不能作为通用敏感内容识别的证明。

效率边界体现在不同任务的打断程度。个人整理直接给结果；草稿可以先修改，不追加发送确认；缺联系人时只补必要事实。用户暂时无法决定，可以保留事项再处理另一件，不需要为继续演示而勉强批准。

透明度边界体现在状态和材料的可核查性。编辑草稿时保留来源，修改后能查看变化；实际结果与准备内容分别标注。响应丢失显示“提交结果尚未确认”，不推断失败或成功。

接管边界体现在控制交还之后还能继续工作。材料对照没有预选，用户需主动选择并说明理由。无法判断可暂缓，再从最近事项找回；受限或暂缓事项可下载含当前内容、原因和未执行范围的人工处理说明。说明需由用户自行交给适当人员，系统没有自动委派。

## 5. 关键交互与异常处理

### 草稿修改

打开草稿后，用户可以保留原文并修改当前内容。保存产生新版本，历史中保留原来的摘录和修改结果。修改后的内容标为人工修订草稿，不再声称逐字来自材料。放弃修改回到已保存版本，不改变来源。

### 材料分歧与人工判断

两份材料同屏对照，桌面并排，手机纵向排列。选项默认均不选中；选择之后仍需写明理由，才可记录判断。结果展示采用哪份、理由是什么，同时保留另一份材料。示例中的“周三”与“周五”不被系统自动裁定。

### 修改后重新核对

修改标题、正文、对象、日期或对照材料后，页面展示变化前后的内容。旧的勾选与选择清空。若另一个页面已经更新版本，旧提交被拒绝，用户需重新核对当前内容。

### 暂缓、取消和结果未知

暂缓保留内容，取消结束本次事项；两者均不批准执行。用户再次打开暂缓事项时重新核对。浏览器提交后没有收到可靠响应时，保留原请求，提供查询与同请求重试，避免重复登记。

当前未决请求仅在当前页面内存中保留，关闭标签后没有跨会话请求恢复保证。测试记录能否经服务进程重启恢复取决于实际存储配置；最近事项列表不能弥补内存存储丢失。

## 6. 建议的现场演示顺序

1. 整理一份个人备忘，查看原内容并撤销，说明低风险任务的事后控制。
2. 准备资料摘录，展开原文，修改并保存草稿，查看新旧内容。
3. 创建缺负责人和日期的协作任务，补齐之后再确认，区分澄清与授权。
4. 准备测试发件，核对后修改正文，观察旧勾选失效；暂缓并刷新后继续。
5. 提出受限承诺，展示限制原因和人工处理说明，指出没有审批或发件发生。
6. 提交两份时间不一致的材料，先暂缓，办理另一件事后重新找回，再记录人工判断。

每个事项都可以独立演示。讲解时先请参与者指出当前状态和下一步，再展开 Risk Lens 讨论处理原因；不把六件事说成系统自动完成的一条长任务。

## 7. 设计评审问题与记录

可结合[桌面材料对照](../../evidence/screenshots/DR0054-human-judgment.png)、[判断操作区](../../evidence/screenshots/DR0054-human-controls.png)、[草稿修订](../../evidence/screenshots/DR0054-draft-edit.png)和[手机界面](../../evidence/screenshots/DR0054-mobile-judgment.png)讨论。图片为测试工作区的工程验证画面，不代表目标用户测试结果。

评审建议覆盖产品设计、业务责任人和实际办公使用者。请参与者在操作前说出预计会发生什么，操作后再对照实际记录。重点记录误解所在页面和具体文案。

| 评审主题 | 需要观察的问题 | 通过条件建议 |
| --- | --- | --- |
| 状态理解 | 是否将草稿、测试记录与真实发件混淆 | 能指出已发生及尚未发生的动作 |
| 核对必要性 | 是否理解同名对象澄清与发送确认的区别 | 不因补齐联系人就认为已提交 |
| 编辑与来源 | 是否把人工改写后的草稿当作逐字原文 | 能找到原文并指出自己的改动 |
| 人工判断 | 是否在未看材料时机械选择 | 能说明选择理由，无法判断时找到暂缓 |
| 修改失效 | 是否理解为什么旧勾选不能沿用 | 能找到变化项并按当前内容重新核对 |
| 暂缓恢复 | 办理另一件事后能否找回原事项 | 原内容仍在，重开没有自动执行 |
| 手机操作 | 长地址、两份材料及退出入口是否易于阅读和操作 | 无页面横向溢出，不需依赖颜色判断 |
| 执行异常 | 响应丢失时会不会另建重复任务 | 使用查询或原请求重试，理解结果仍待核对 |
