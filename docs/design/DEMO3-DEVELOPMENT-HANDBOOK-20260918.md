# Demo3 开发版指导手册与设计评审

版本 1.1 · 2026-09-19；保留原文件名供已有链接使用。

本文用于产品实现与联调。对外材料为[人机共驾设计指导手册](submission/人机共驾设计指导手册_v1.0.md)和[边界情形与接管案例库](submission/边界情形与接管案例库_v1.0.md)。两版沿用相同的 R01-R16 规则与 C00-C12 案例编号；对外版讨论可复用设计原则，本文记录实现取舍、接口和未覆盖项。

## 1. Demo3 要展示什么

Demo1 展示单个长任务的拆分推进，Demo2 展示多个任务的规划与并行，Demo3 展示不同简单事项中的一次业务动作。一个动作可以经历补信息、修改、确认和暂缓，这些是同一动作的交互过程，不再拆成一串业务任务。

三种演示使用同一工作台。Demo2 的多 Worker 仍属目标能力，不能用现有分支列表当作并行执行证据。Demo3 在现有中心工作区增加“办理事项”，继续使用左侧资料预览、右侧操作轨迹和同一 Run 状态系统。页面不增加 Demo 或场景编号选择器。

参考《网页演示.html》的内容核对和 Risk Lens 层次，以及《人机交互边界.png》的安全、效率、透明度、接管四类边界。布局沿用当前前端，不整页复制历史原型。主要需求依据是 `office_mobile_scenarios_v7_from_v5_demo_focused_client_ready.md`；L0-L5 与 AL0-AL5 分别记录。

## 2. 当前六类事项

| 事项 | 对应案例 | 服务端处理 | 用户操作 | 完成证据 |
| --- | --- | --- | --- | --- |
| 整理个人文本 | C01，L1/AL4 | 去除行首尾空白、合并空行，保存独立文本记录 | 查看整理前内容、下载、撤销 | 回执含处理后文本；撤销后内容恢复原值 |
| 准备资料摘录 | C02，L2/AL2 | 逐字摘录最多 1200 字符；保存最多 5000 字符的人工修订 | 对照来源、原位编辑、保存、下载 | 新草稿版本及历史 content_snapshot；原文保留 |
| 创建协作任务 | C03、C06，L3/AL3 | 检查内部负责人、日期和内容，等待确认 | 补齐字段、修改、确认、暂缓、取消 | 生成一条测试任务回执 |
| 发送汇报内容 | C04、C08、C09，L4/AL3 | 展示完整正文与测试联系人，要求核对对象、正文、影响 | 三项核对后确认，或修改、暂缓、取消 | 生成一条测试发件回执 |
| 受限业务请求 | C05，L5/AL1 | 阻止受限动作；发送文本中的指定受限词同样拦截 | 查看原因、下载人工处理说明 | denied 状态，无执行回执 |
| 核对材料分歧 | C11，L2/AL1 | 并列保留用户提供的两段非敏感材料，不自动判断真伪 | 选择 A/B、填写理由、记录判断，或暂缓/修改/取消 | decision_note 回执与 decision；两份原文不变，无后续任务 |

所有文本都允许用户填写。示例联系人使用 `example.invalid`，不会通知真实同事或发送邮件。六类事项都不调用模型。文本整理不包含 DOCX/PPT 排版；摘录不称为摘要，也不声称理解原文。任务与发件是服务端 Snapshot 内的隔离测试记录，不是已经接通的企业系统，不属于既有 Artifact/EffectReceipt 验证成果。

发送检查只匹配“最低折扣”“最低价承诺”“无须审批”三个示范词，以及明确选择的受限操作。它不是通用敏感内容识别器，也不支持通过换一种说法自动判断价格政策。实际接入前必须由业务策略和权限系统补齐。

## 3. 两版的规则对应

| 对外规则 | 本次落点 | 覆盖边界 |
| --- | --- | --- |
| R01 动作范围 | 每个 Run 只有一个 action；正文、对象、影响同屏 | 没有复合自然语言任务拆解 |
| R02 资料与不可信内容 | 资料只经现有 allowlist 安全预览；原文不被执行 | 不向模型传送；未验证通用提示注入防御 |
| R03 受限处理 | 服务端 denied；通用 resume 不能代替确认 | 正式审批、身份和组织授权未接入 |
| R04 缺信息澄清 | 缺联系人、日期、内容时 needs_input | 固定测试通讯录，不查询企业通讯录 |
| R05 准备与提交 | draft_ready、awaiting_confirmation、executed 分开 | executed 只表示对应测试记录已形成 |
| R06 核对依据 | 来源摘录、原文预览、整理前内容、完整对象 | 没有语义正确性证明 |
| R07 确认工作 | L3 普通确认；L4 三项核对 | 三项勾选是设计假设，未证明降低误批率 |
| R08 版本绑定 | Run version 和 action revision 双重检查；修改后清空核对 | 不包含附件、审批到期或外部权限动态变更 |
| R09 结果未知 | 保存原请求与幂等键，查询状态或重试同一请求 | 当前页保留；关闭标签后未决请求缓存不持久化 |
| R10 接管上下文 | 保留材料、判断理由与暂缓状态；最近事项可重新打开；下载人工处理说明 | 仅最近 20 个 Run 内的事项，无完整待办箱或自动委派 |
| R11 恢复范围 | 保留修改历史，区分取消、暂缓与撤销 | 不支持召回真实邮件 |
| R12 长期偏好 | 保留为后续设计要求 | 不持久化“以后不用问” |
| R13 手机核对 | 窄屏布局、完整地址、正文、暂缓 | 无语音确认、设备检测或跨设备接续保证 |
| R14 实际撤销 | 个人文本恢复原值，保留撤销时间；摘录支持原位保存人工修订 | 文本副本撤销；草稿历史可查，未新增草稿历史回滚 |
| R15 服务端执行约束 | 风险、确认条件、终态均由固定服务端策略产生 | 未接生产级 Policy/Permit 或工具网关 |
| R16 可追查记录 | history 保存各版输入及每次动作 | Snapshot 内记录，非独立合规审计账本；最多 60 条 |

## 5. 页面和状态

首屏为事项类型、标题、内容及必要字段。主按钮“开始办理”提交结构化输入。个人文本直接出现结果及撤销；摘录出现草稿；协作任务出现普通确认；发件出现核对区；受限请求出现原因与人工办理说明。

待确认状态首屏显示对象、正文、日期，Risk Lens 说明处理原因、影响和恢复范围。L4/L5 默认展开。操作记录默认折叠。内部幂等键、运行 ID 和调试信息不占用主操作区。

| 状态 | 允许动作 | 后续 |
| --- | --- | --- |
| needs_input | 补齐并重新核对、取消 | 新内容 revision 加 1，再评估 |
| awaiting_confirmation | 确认、修改、暂缓、取消 | 只有当前版本和必要核对齐全才能确认 |
| deferred | 继续核对、修改、取消 | 不自动执行 |
| draft_ready | 查看来源、编辑并保存草稿、下载、办理另一件 | 保留来源和各版草稿；编辑增加 revision |
| awaiting_decision | 选择材料并填写理由、修改、暂缓、取消 | record_decision 形成 decided，不执行后续事项 |
| decided | 查看选择与理由、下载判断记录、办理另一件 | 两份输入不变；不冒充业务批准 |
| executed | 下载；个人整理可撤销 | 不重复确认 |
| denied / cancelled | 查看记录、办理另一件 | 无执行回执 |
| undone | 查看恢复内容、下载 | 不重复撤销 |

`stale` 是保留状态；目前版本竞争返回 HTTP 409，刷新最新内容并清空本地核对项，不会自动把服务端状态写成 stale。网络异常显示“提交结果尚未确认”，不能显示“发送失败”后直接创建第二个请求。

## 6. 前后端接入

`OfficeActionWorkbench` 嵌入 `harness-workbench.tsx`；`office_action_policy.py` 负责固定规则；`HarnessRuntime` 使用既有 owner、版本、事件和幂等存储。新增类型位于 `packages/contracts/office_actions.py`。

开始仍用 `POST /v1/harness/runs`，增加可选 `action`。普通资料研究不传此字段，继续原 Agent Control Loop。事项路径不启动 Planner/Analyst，轨迹明确显示未调用模型。

控制使用 `POST /v1/harness/runs/{run_id}/action-controls`，包含 `command`、`expected_version`、`action_revision`、`idempotency_key`；修改带 `replacement`，确认带 `reviewed_fields`。风险、自主程度、回执不能由客户端指定。

服务端先检查 Owner、版本和允许的状态转换，再形成新的 Snapshot 和有序事件，与幂等记录一同写入。保存失败恢复内存中的旧状态，不返回执行成功。相同请求重放返回原回执；同一键携带不同内容被拒绝。修改只允许原操作类型，不能借修改把受限事项切换成另一种操作。

`office_action` 保存输入、策略版本、状态、风险、自主程度、预览、必要核对、回执和历史。所有回执标记 `external_action=none`，事项标记 `execution_environment=isolated_test_records`、`model_called=false`。

未配置数据库时使用单进程 memory，重启丢失记录。使用持久化 store 时恢复已有事项 Snapshot，不重放动作。现有 PostgreSQL 基础设施不等于本次已经完成真实数据库重启验证；跨实例一致性也不在本次范围。`X-User-Id` 仍是未签名演示身份。

## 7. 设计评审记录

这是基于需求和代码的设计自查，尚无目标设计人员参加的正式评审或可用性研究。反馈与签字不得由开发记录代填。

| 评审问题 | 处理结论 | 仍需验证 |
| --- | --- | --- |
| 六种任务是否各自构成单步演示 | 每种只处理一个事项；人工判断记录不自动启动新任务 | 参与者是否理解此区分 |
| 是否保持统一工作台 | 使用原中心区、资料预览、右侧轨迹和 Run | 与研究任务切换的发现成本 |
| 低风险是否被强制弹窗打断 | 个人整理直接执行，并给出真实撤销 | 自动整理后是否易于发现变化 |
| 普通确认与强确认有何区别 | L3 核对字段；L4 逐项核对对象、正文、影响 | 勾选是否机械化、是否漏读正文 |
| 受限动作如何结束 | 原因可读，无继续执行按钮；说明正式审批未接入 | 业务方是否认可受限词与流程 |
| 修改、重复点击、断线会怎样 | 版本失效、幂等重放、结果未知分别处理 | 跨标签页、进程重启和真实连接器故障 |
| 是否夸大为实际办公接入 | 所有页面与回执写明测试记录，无真实发件 | 接入后仍需保留准确的结果语义 |

演示顺序建议为：个人整理并撤销；资料摘录并查看来源；缺联系人和日期的协作任务，补齐后确认；发件核对后修改正文，确认旧勾选被清空，再暂缓、刷新、继续；最后展示受限承诺。同一任务之间使用“办理另一件事项”，不自动串行运行这些事项；增加材料对照、暂缓后办理另一件、再从最近事项找回并记录判断的路径。

后续设计人员评审可按案例库分别记录：用户认为已经发生的动作、认为接下来会发生的动作、遗漏的核对信息、误确认与恢复路径。修改方案时同时更新 R/C 对应表。正式业务接入优先补身份与授权、业务规则、连接器结果查询及去重、审批失效条件，随后再讨论偏好学习与跨设备接续。

## 9. 2026-09-19 开发补充

主分支整合补充：六类事项现在也通过同一个 Task Ledger 形成独立 Task/Run；任务会话和能力页可打开，Task 指针未核对通过时不允许修改。研究/continuation/Worker 路径保持主分支合同，完整记录见[合并证据](../evidence/DEMO3-MASTER-MERGE-20260919.md)。合并后公开 API 为 12 个 path、13 个 operation。

[DR-0065](../decisions/DR-0065-demo3-editable-drafts-and-human-judgment.md)、[SCENARIO-052](../scenarios/SCENARIO-052-demo3-human-judgment-and-return.md)与[运行证据](../evidence/DR-0054-DEMO3-COLLABORATION-EVIDENCE-20260919.md)记录本轮增量。

compare_materials 接受 content/alternative_content 两段用户材料，完整时 awaiting_decision。record_decision 必须携带 selected_option=first/second 与非空 rationale，保存 decision 和 decision_note 回执，映射为 decided/completed。普通 confirm 无法代替判断。edit_draft 只接受 extract_excerpt/draft_ready，更新 preview/receipt.content，保留 source_excerpt 和历史 content_snapshot。两种命令复用既有 Owner、version、revision、幂等和持久化检查。

最近事项复用 GET /runs?limit=20，重新打开使用 GET 当前 Run，不会继续任务。内容修改差异来自服务端历史输入和当前输入。人工处理说明由浏览器下载当前已保存内容，不会发起审批或通知。新增两类命令事件已经接入原有 SSE；不新增公开路径、模型调用或业务连接器。
