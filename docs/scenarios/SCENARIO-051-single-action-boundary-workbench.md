# SCENARIO-051：在同一工作台办理不同单步事项

合并说明：本记录从 Demo3 分支旧编号迁入，原实现提交为 `f01a903`。主分支原有编号不变；历史 Evidence 保留当时的编号和测试范围。最新兼容性检查见[主分支合并记录](../evidence/DEMO3-MASTER-MERGE-20260919.md)。

状态：Limited Verified，限固定策略、测试记录与单进程；执行证据见 [DR-0064 Evidence](../evidence/DR-0053-SINGLE-ACTION-EVIDENCE-20260918.md)。

目标用户是需要整理、准备资料、安排协作或发送汇报的办公人员；设计评审人员观察每种事项为何采用不同介入方式。触发是用户需要完成一个具体动作，痛点是每种动作都弹同样的确认框，或将准备内容误认为已经提交。

完成条件：低风险整理能够恢复原内容，摘录可对照来源，任务与发件只有在条件齐全后生成一条测试回执，受限动作始终无执行回执。真实业务系统接入不属于此完成条件。

正常路径从“办理事项”开始。用户选择操作并填写内容，服务端判断准备状态；用户依据对象、内容与影响补信息或作决定；界面显示服务器返回的实际结果。不同事项由用户分别创建，互不构成任务链。

异常路径包含同名联系人未选定、日期缺失、内容修改导致旧确认失效、重复点击、提交响应丢失、受限内容、持久化失败，以及暂缓后刷新。对应处理分别是澄清、版本冲突刷新、原请求幂等重放、拒绝执行、保持旧状态和读取原 Snapshot。

前台保留正文、对象、日期、Risk Lens 和折叠历史；主界面隐藏内部幂等键。强确认默认不能点击，完成当版必要核对后才开放。关闭页面不构成授权。

后端事实来自 `office_action.status/revision/required_checks/receipt/history`，Run version 和 event sequence 单调增长；Owner 与幂等存储沿用 Harness。普通 Loop controls 不可用于跳过动作控制。

来源为 `USER-FEEDBACK-20260918-DEMO3-HANDBOOK`、v7 需求和已有边界原型，均属于设计需求而非用户实验。完整规则、案例及未覆盖项见[开发版手册](../design/DEMO3-DEVELOPMENT-HANDBOOK-20260918.md)。
