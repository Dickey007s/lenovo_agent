# SCENARIO-075：系统先做能做的，人在具体边界参与

状态：Limited Verified。日期：2026-10-24。Decision：DR-0088。
来源：USER-FEEDBACK-20261024-HUMAN-AGENT-DIVISION。

## 案例和验收

| 案例 | 输入 | 系统负责 | 人负责 |
| --- | --- | --- | --- |
| 按明确例外整理权限 | 吴嘉木的入职 CSV + 软件分配 PDF | 应用“个人备注优先”，保留通用软件，不开通研发专属软件 | 无须重复决定已有明确规则 |
| 有余额，不等于已收款 | 2026往来明细.xlsx | 展示期初150万元、借方变动20万元、期末170万元及来源行 | 补足真实银行回单，不能凭账面余额判断到账 |
| 变更例外，先交负责人 | 同一入职资料 + 尚未批准的 GitHub Enterprise 变更要求 | 整理通用软件清单、定位不开通备注与覆盖规则 | 选择维持现规则或仅整理变更申请；不执行账号开通 |

完整可重复指令位于 `apps/web/app/task-journey.tsx` OFFICE_EXAMPLES 后三项；UI 默认折叠为“更多人机分工示例”。每项显式 analysis_only。

## 主流程

1. 点击示例，只填草稿；展示预计输入和交付目标，没有网络 POST。
2. 提交后真实 Planner/Analyst 在服务端批准范围处理。
3. 等待或结束时，显示系统已处理、需要人参与以及 Agent 尚未完成的工作。
4. 明确规则直接应用；缺源不冒充完成；来源定位失败不把技术责任转给用户。
5. 人工取舍页面显示原文、问题、理由、互斥选项及确认后仅分析的范围，无默认选项。
6. 实测选择“维持现规则”，写入版本化决定回执，/continue 新建同 Task 后续 Run，返回带证据的新清单。

## 反例

- 有 Anchor 但只有 context，或绑定 Branch 仍 waiting，不能列为系统已完成。
- 部分规则或来源冲突已经由明确优先级消解，不应该再要求业务负责人裁决。
- 协作用量授权不是低置信判断；automatic_readonly 不引入人工派发。
- 已通过文件检查不能抵销业务 Gate 的失败。
- 历史只读、未完整的待决、失败和预算限制不能被两个分工栏隐藏。

## 剩余边界

银行回单案例只完成缺源识别和已知余额保留，没有文件上传、补齐资料后自动闭环。权限案例仅核对/整理，不验证任何真实人的审批资质，也不执行开通。实测是助手走查，不等于目标用户已经理解。
